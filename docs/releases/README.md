## 범위와 판정

kmp_agent는 공통 기능·실행 방식·사용 전제·제약을 관리한다. 적용 프로젝트는 제품 목표·명세·디자인·코드·테스트·실제 사용 결과를 자체 보관한다. 특정 제품의 목표·개발 상태는 이 기록의 필수 입력이나 평가 대상이 아니다. 공통 예제는 하네스 시험 자료이며 제품 채택·제품 전체 흐름 성공을 의미하지 않는다.

- 구현 상태: **구현 / 부분 구현 / 문서만 있음 / 없음 / 확인 불가**. 요청한 흐름 전체와 실제 제공 부분을 함께 적는다. 적용 프로젝트 실행이 없다는 이유로 코드를 미구현이라 하지 않는다.
- 실행 방식: **수동 명령**, 그 **명령 내부 자동 처리**, **역할 간 자동 연쇄 실행**을 분리한다. 명령이 필요하거나 상위 Codex가 다음 호출을 결정하면 무지시 자동 연쇄가 아니다.
- 검증 범위: **미실행 / 단위 테스트 / 로컬 통합 시험 / 공통 예제 실행 / 실제 적용 프로젝트 실행**. 확인한 범위를 병기하고 대상 기능·환경을 한정한다. 임시 Git 대상은 실제 적용 프로젝트가 아니다.
- 코드·테스트 파일은 구현/시험 가능성의 근거다. 실행 기록은 실제 관측 범위의 근거이며 테스트 코드 존재만으로 통과했다고 쓰지 않는다. 기록과 현재 코드의 동일성이 입증되지 않으면 과거 검증으로 표시한다.
- Git 제외 로그·스냅샷은 보유 환경에서만 확인 가능하다. 새 설치에 포함되거나 누구나 재현 가능하다고 주장하지 않는다. 검증 시점·미실행·UNKNOWN을 보존하고 비공개 원문/경로/제품 내용을 복사하지 않는다.

## 설치한 버전 찾기

1. 적용 프로젝트의 `.kmp-agent/installation.json`에서 `version`, `requested_ref`, `commit`, `mode`를 확인한다. [status](../installation.md#프로젝트-명령)의 실제 runtime_identity와 선택 SHA/dirty도 대조한다. status는 읽기 점검 명령이며 VERIFIED는 해당 연결·수집 범위이지 제품 개발 PASS가 아니다.
2. 이 목록에서 해당 태그의 문서를 찾고 **커밋까지 일치하는지** 확인한다. VERSION 문자열만 같은 개발 작업본을 정식 배포판으로 간주하지 않는다. 설치 코드가 dirty하거나 개발 모드이면 해당 변경은 별도 근거로 관리한다.
3. 앞으로 게시하는 버전은 해당 태그의 `docs/releases/<태그>.md`를 함께 제공한다. `v0.1.0` 태그에는 이 새 경로가 없으므로, 원본 저장소의 현재 지원 목록에서 이 사후 기록을 찾는다. 이번 작성물은 아직 미커밋·미게시이므로 원격에 문서가 있다고 가정하지 않는다. 전체 SHA 설치가 목록의 태그 SHA와 다르면 정확한 버전의 현황은 확인 불가로 두고 해당 소스를 점검한다.
4. 제품에서 확인한 실행 결과는 제품 저장소에 보관하고 하네스 버전·SHA와 연결한다. 지원 현황은 설치 가능성과 제공 계약을 설명하며, 프로젝트의 검증 결과를 대체하거나 자동 업로드하지 않는다.

## 릴리스 준비·보존·정정

1. 릴리스 준비에서 기존 VERSION·예정 태그·후보 커밋을 선택하고 [버전업 지침 정비](#instruction-maintenance)를 수행한다. 정비 결과를 반영한 후보 파일로 9개 흐름을 점검한다. 현재 작업본 문서 전체를 배포판으로 단순 복사하지 않는다. 코드 변경이 있으면 영향 행과 검증 근거를 다시 확인한다.
2. `docs/releases/<예정 태그>.md`에 구현/실행/검증/사용 전제/근거·점검 시점·재실행 여부를 확정한다. 후보가 아직 미커밋이면 작업본으로 남기며 배포 완료라 하지 않는다. 이 단계에서 [본문 지침·템플릿](#github-release-본문)으로 Release 초안을 작성한다. 태그 확정 시 최종 커밋과 문서의 범위를 대조하고 기존 작업·릴리스 승인 근거에 실제 SHA를 연결한다. 자기 파일을 포함하는 미생성 커밋 SHA를 만들어 적지 않는다.
3. 기존 작업·릴리스 승인 규칙에 따라 커밋·태그·게시를 별도 수행한다. GitHub Release 본문은 최종 배포 커밋과 원격 설치 검증 결과를 반영한 뒤 확정·게시한다. 이 절은 자동 릴리스나 승인 게이트의 구현을 의미하지 않는다. 배포 후 이 목록에 실제 태그/SHA를 연결하고 이전 배포 기록은 보존한다. 이번 문서화 작업은 커밋·태그·게시를 수행하지 않는다.
4. 배포 기록 오류는 이후 저장소 변경에서 해당 문서에 **정정 일자·대상 주장·수정 이유·근거**를 추가한다. 기존 태그 이동·과거 실행 근거 재작성·결과 삭제로 고치지 않는다. 옛 설치에 정정이 자동 반영된다고 주장하지 않는다.
5. 개발 중 진행 상태는 기존 task/run/검증 기록이 원본이다. 매 작업 완료마다 이 문서를 갱신할 의무는 없다. 릴리스 준비·배포 확인·중요 오류 정정 시 갱신한다. 과거 모든 배포판의 소급 조사는 요구하지 않는다.

## 버전업 지침 정비

patch·minor·major를 포함한 하네스 버전업의 릴리스 준비 단계에서, 최종 후보·버전을 확정하기 전에 메인이 [지침 정비 담당](../roles/instruction-maintainer.md)을 실제로 한 번 호출한다. 직전 실제 배포 태그/커밋부터 현재 후보와 미커밋 변경까지 누적된 지침을 함께 점검한다. PR 생성·리뷰·머지마다 정비 담당을 호출하지 않는다. 버전 문자열을 먼저 바꿨더라도 정비를 생략하지 않는다.

흐름은 **변경 누적 → 버전업 준비 → 담당 계획 확인·정비 호출 → 메인 검토·수정 반영 → 영향 검증 → 후보·버전 확정 → 별도 승인된 배포**다. 정비 결과는 이번 버전 후보에 포함한다. 의미 보존 정리와 행동·권한을 바꾸는 정책 제안을 구분하며, 미확정 정책을 임의로 채워 정비 완료로 처리하지 않는다.

평소 정비할 문제는 기존 작업/실행 기록에 근거·영향 지침·다음 행동과 함께 모은다. 현재 작업을 잘못 수행하게 만드는 충돌은 즉시 처리하고 그 조치도 다음 버전의 누적 점검에 포함한다. 즉시 처리할 때도 확인이 필요한 정책은 기존 질문·승인 규칙을 따른다.

담당은 계약에 따른 비교 범위·수정 경로와 해시·검증·남은 문제를 반환한다. 메인은 실제 호출 근거와 별도로 결과 수락을 기록한다. 호출할 수 없거나 정비·메인 검토가 끝나지 않으면 사유·남은 범위를 남기고 지침 정비 및 릴리스 준비 완료로 표시하지 않는다.

메인 수락 뒤 후보가 바뀌면 정비 결과의 유효성에 미치는 영향을 확인한다. 지침 의미·연결·관련 코드 동작에 영향이 있으면 해당 범위만 다시 검토하고 결과·해시를 갱신한다. 영향이 없으면 판단 근거를 남기며 전체 정비를 반복하지 않는다.

이 절은 메인이 수행하는 지침 계약이다. 자동 서브에이전트 생성기·버전 변경 감지기·런타임 릴리스 차단 게이트를 구현한 것이 아니며, PR 제출 권한을 머지·태그·배포·설치 승인으로 확대하지 않는다.

## GitHub Release 본문

이 절은 공통 작성 지침·템플릿의 원본이다. 지원 현황 표는 기능별 계약·근거의 원본으로 유지하고 Release 본문은 사용자에게 중요한 동작·영향만 요약해 해당 태그의 문서로 연결한다. 별도 상태표 버전이나 자동 집행 기능을 만들지 않는다. 버전별 초안은 `docs/releases/<태그>-notes.md`에 보관한다. [v0.2.0 본문 원본](v0.2.0-notes.md)은 태그 뒤 확정하는 SHA·원격 검증 결과만 게시 본문에서 대입한다. 게시된 본문에는 치환 필드를 남기지 않고, 태그의 원본과 최종 게시 본문 대응 근거를 릴리스 기록에 보관한다.

### 작성 기준

- 한국어로 간결하게 작성한다. 이번 버전에서 사용자가 새로 할 수 있는 일을 먼저 쓰고, 내부 파일·커밋 목록으로 대신하지 않는다.
- 비교 기준은 직전 **배포 태그/커밋**이다. 추가·변경·수정·제거 중 실제 해당 항목만 남긴다. 미배포 후보 사이의 실험이나 다음 버전 계획을 출시 기능으로 쓰지 않는다.
- 수동 호출, 명령 내부 자동 처리, 역할 간 무지시 자동 연쇄를 구분한다. 부분 지원·미지원·알려진 문제와 사용 전제를 숨기지 않는다. 상세 표를 복제하지 말고 배포 태그에 고정한 지원 현황을 연결한다.
- VERSION·태그·태그가 가리키는 최종 배포 커밋·지원 현황을 대조한다. 임시 로컬 Git SHA를 최종 배포 SHA로 쓰지 않는다. 초안의 미확정 값은 표시하고 게시 전 확정한다.
- 설치·update 명령은 해당 태그의 실제 CLI·소스 URL·ref 정책에 맞춘다. 명령은 검토/시험 목적으로만 제시하며 본문 작성 중 실행하거나 배포 권한으로 해석하지 않는다.
- 설정 변경·재초기화·훅 재등록/신뢰·새 세션·별도 후처리와 직접 참조 모드의 전환 조치를 확인한다. 깨지는 호환성·데이터/로그 형식 영향을 설명한다. “추가 조치 없음”·“완전 호환”은 해당 경로의 검증 근거가 있을 때만 쓴다.
- 검증은 **최종 배포 커밋에 적용되는 범위**로 쓴다. 후보 간 코드/입력이 같아 과거 결과를 유지하면 내용 해시와 변경 영향·추가 검사 근거로 연결한다. 테스트·로컬 설치·공통 예제·실제 적용 프로젝트를 구분하고 미실행/미확인을 명시한다. 개별 PASS나 공통 예제 성공을 제품 전체 실사용 성공으로 확대하지 않는다.
- 개인 절대 경로·로컬 file URL·개인 정보·비밀 값·원본 로그·비공개 제품 내용을 싣지 않는다. CLI의 공통 상대 경로와 치환할 입력은 허용하되 개인 환경값을 넣지 않는다. 링크는 `https://github.com/<owner>/<repo>/blob/<tag>/...`처럼 배포 태그에 고정한다. 이동하는 main/HEAD, 로컬 `.harness/` 근거, 임시 후보 SHA 링크로 공개 근거를 대신하지 않는다. 비공개 근거는 범위만 요약한다.
- 자동 생성한 초안도 실제 이전 태그 대비 diff·지원 현황·검증 근거와 사람이 대조한다. 미확정 표시·접근 불가 링크·잘못된 명령이 남으면 게시 보류다.

### 준비·확정·게시·정정

1. 릴리스 준비 단계에서 아래 템플릿으로 초안을 작성한다. 다른 세션의 배포/편집 상태를 확인하고 고정 후보가 있으면 원본 검증 기록을 보존한다. 추가 문서는 후보 후속 변경으로 분리한다.
2. 최종 후보에 반영할 때 manifest·문서 해시를 다시 고정하고 변경 영향에 해당하는 검사를 수행한다. 코드/입력이 동일한 문서 변경 때문에 기존 실행을 소급 실패 처리하지 않으며, 새 문서가 예전 후보에 포함됐다고 표시하지도 않는다.
3. 별도 승인된 배포 절차에서 최종 커밋·태그를 확정하고 실제 원격 태그/SHA 설치·업데이트 결과를 대조한다. 최종 커밋 적용성·마이그레이션·공개 링크를 확인한 뒤 GitHub Release 본문을 확정·게시한다. 원격 검증이 미실행이면 초안 상태를 유지한다. 태그 설치와 설치본 Codex 세션·제품 전체 검증은 각각 별도다.
4. 게시 뒤 오류 정정은 본문에 **정정 일자·대상 설명·수정 이유·근거**를 남긴다. 코드 변경이면 새 버전으로 배포하고 기존 태그는 이동하지 않는다. 과거 검증 기록도 덮어쓰지 않는다.

현재 구현은 **문서 지침·수동 작성/대조 절차**다. 자동 초안 생성기, 최종 SHA/원격 검증을 강제하는 게이트, 자동 Release 게시·정정 기능은 구현했다고 보고하지 않는다. 이 절 자체는 커밋·태그·푸시·게시를 실행하거나 승인하지 않는다.

### 본문 템플릿

아래 틀을 복사하되 대괄호 입력과 불필요한 변경 종류는 게시 전 제거한다. 이 틀 외에 동일한 템플릿을 다른 문서에 복제하지 않는다.

````markdown

## 이전 배포 버전 대비 변경

비교 기준: [직전 태그] → [이번 태그].

- 추가: [해당하면 기능·사용 방식·영향]

- 수정: [해당하면 문제의 조건과 해결된 동작]
````
