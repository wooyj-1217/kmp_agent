# 프로젝트 단계 계약 분기 시험

이번 범위는 kmp-agent 공통 규격·작업 게이트이며 제품 구현이나 기술 스택 선택이 아니다. 기존 메모의 requirements.md를 임시 작업 입력으로 읽어 분기 시험을 수행했다. P-004/D-004·승인 산출물·과거 연결 보고서는 변경하지 않았다.

## 변경

- [프로젝트 설정](../../project-settings.md)과 [JSON 템플릿](../../templates/project-settings.json): 구현 타깃·UI 기술·지원 범위·공유/플랫폼 책임과 소유 모듈, 서버 없음/기존/신규, 해당 서버·DB·API·정책·실행·검증 결정을 확정/제안/미정/해당 없음으로 구분한다.
- [개발 템플릿](../../templates/development-plan.md): API·정책 책임, 실행 명령·환경변수 자리표시자·DB 준비/마이그레이션/실패 복구, 타깃별/전체 연결 수용 기준은 원본 참조로 연결한다. 비밀값을 넣지 않는다.
- 기존 tasks.yaml의 stage_contract에 설정과 문서의 불변 artifact 입력을 연결했다. 명시적 configure-stage 후 ready/begin/handoff에서 해당 단계의 필수 결정만 검사한다. 역할 컨텍스트·입력 receipt에도 기존 입력으로 전달한다. 별도 상태·버전 체계는 없다.
- integration_verification의 PASS는 실제 모드·출력 hash·전체 선택 타깃 결과·연결 관측 근거를 요구한다. 기존 검증 기록·검토 절차를 사용한다.

## 실제 실행한 분기 검증

[test_project_contract.py](../../../harness/test_project_contract.py)의 6개 시험이 실제 로컬 Tasks 상태 전이와 입력 snapshot을 사용했다. 각 시험은 임시 폴더에서 격리했으며 기술 값·API 문서·검증 보고는 **합성 fixture**다. 실제 API·서버·DB 실행으로 보고하지 않는다.

| 분기 | 관측된 하네스 결과 |
| --- | --- |
| 서버 없음 | 서버/DB/API/정책/마이그레이션 해당 없음과 이유를 확인. UI READY 가능. 불필요한 서버 구현 작업은 NOT_APPLICABLE로 거절 |
| 기존 서버 | API 미정이면 클라이언트 착수 거절. 계약 확정 후 READY. 소유하지 않는 내부 DB/마이그레이션은 해당 없음 허용 |
| 신규 서버 | 제안 상태 마이그레이션은 서버 착수 거절. 확정 문서 snapshot 후 READY. UI 기술 미정은 서버 작업을 막지 않음 |
| API 미정 | 같은 검토 완료 선행 작업에서 UI 인계 READY, 클라이언트 실연동 인계는 거절되고 TODO 유지. 실패 인계 기록/입력 부분 변경 없음 |
| 목 계약·원본 수정 | mock 계약을 real로 원본 파일만 고쳐도 동결된 기존 입력 때문에 실연동은 거절. 명시적 재설정 후 READY |
| 통합 검증 접수 | mock PASS와 웹 결과 누락 PASS는 거절. 정확한 출력 hash·모든 타깃·관측 필드를 갖춘 합성 보고만 스키마 검사 통과 |

집중 시험: `rtk proxy python3 -m unittest harness.test_project_contract -v` — 6개 PASS, 6.764초. 전체 회귀 93개 PASS(177.287초), diff 공백 검사·Python 구문 검사·설정 스키마·문서 링크 검사 PASS. [시험 근거](evidence/project-stages-tests.json)에 기록했다.

## 한계·후속

이 검증기는 설정/증거의 상태·참조·해시·타깃 범위를 검사한다. 문서 내용의 정책 적정성이나 실제 통합 실행을 자동 증명하지 않는다. 검토자는 기존 역할/인계 규칙으로 계약 내용과 실행 근거를 확인한다. 필수 값에 제안이나 목 결과를 확정으로 표시해서 우회하면 안 된다.

기존 단계 미지정의 기획·디자인·입력 해석 시험은 원래 계약을 유지한다. 실제 구현 배정에서는 명시적으로 단계를 지정한다. 자동 단계 추론·설정 전파는 미구현이다. 대상 프로젝트의 UI/서버/DB 기술·API 정책·명령 확정, 실제 앱·웹→API→서버→DB 저장/재조회·재시작 유지·실패 경로는 모두 향후 작업/NOT_RUN이다.
