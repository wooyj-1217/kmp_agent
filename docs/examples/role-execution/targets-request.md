# CR-003 — 진행 중인 즐겨찾기 예제에 앱·웹 디자인 범위 추가

후속 사용자 요청을 기존 CR-002·작업·기준본에 통합한다. 첫 기획 실행을 취소하거나 원본을 삭제하지 않는다. 이미 생성한 P 기준본은 보존하고 해당 작업의 추가 시도로 누락된 타깃 명세를 갱신한다.

이번 합성 예제의 디자인 타깃은 앱용 HTML 시뮬레이션 390×844, 반응형 웹 모바일390×844·데스크톱1280×900이다. 이것은 실제 제품 지원 OS/브라우저/접근성·KMP 웹 빌드 채택 확정이 아니다. 해당 지원 버전은 UNKNOWN으로 둔다. 기존 즐겨찾기 기본/반전/표시/안정 정렬 정책은 타깃 공통이다.

기획은 각 REQ/POL/AC에 app/web 적용·공통 의미/플랫폼 차이를 명시한다. 공통 데이터·상태를 공유하지만 입력/포커스·내비게이션/스크롤은 타깃별로 설계한다. 앱은 작은 화면의 목록↔상세 이동·터치·뒤로가기, 웹은 모바일 단일 열 및 데스크톱 목록+편집 분할 배치·Tab/Enter/Space/포커스를 구분한다. 예제 범위만 합성 결정으로 기록하고 실제 지원 범위를 추정하지 않는다.

디자인은 prototype/app-favorites.html과 prototype/web-favorites.html을 각각 생성한다. 웹은 데스크톱에서 넓어진 앱이 아닌 분할 목록/편집 구성과 적절한 키보드 동작을 사용한다. 공통 tokens.css와 즐겨찾기 컴포넌트 의미·상태를 공유하고 app.css/web.css 등 표현 차이는 명시적으로 분리한다. 공통 컴포넌트 갤러리에는 앱·웹 표현과 상태가 있어야 한다. 현재 index.html은 두 실행 진입점을 링크한다. 모든 즐겨찾기 버튼은 ACT-FAV-TOGGLE·data-memo-id를 유지한다. 필수 상태는 타깃마다 목록 초기/즐겨찾기/해제/빈 목록·편집/저장 중/성공/오류·재시도를 포함한다. UI에 하네스 검증 상태는 표시하지 않는다.

target_artifacts 응답은 app / web-mobile / web-desktop 각각 entry·screens·requirements를 갖는다. 웹 두 entry는 동일 HTML을 가리켜도 된다. 같은 D 기준본에 세 타깃의 문서·토큰·컴포넌트·시안을 함께 제출한다. 검토 보고서는 REQ→타깃→SCREEN/STATE/ACT→결과·캡처를 연결한다. 일부 타깃만 PASS여도 전체 완료로 처리하지 않는다. 앱 HTML의 브라우저 렌더링·조작과 실제 네이티브 실행·시스템 뒤로가기·키보드·접근성 검증을 구분하며 네이티브는 NOT_RUN이다.

반환 경로용 합성 결함은 앱 후보 한 타깃에만 넣을 수 있다. 웹은 이전 렌더링 근거·동등성으로 연결하고 앱만 새 렌더링을 확인한다. 개발 해석 계획은 디자인 대상 app/web과 실제 KMP 앱/플랫폼 구현 채택을 구분해야 한다. 웹 빌드 타깃 추가·KMP 앱 구현·빌드는 진행하지 않는다.
