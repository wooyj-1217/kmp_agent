# 착수 계획과 필수 답변 대기

전체 실행 계획은 메인이 만들고, 위임받은 작업의 상세 계획은 담당자가 만든다. 계획에는 무엇을 바꾸는지뿐 아니라 완료 조건, 입력, 출력, 확인 방법을 포함한다. 서브에이전트를 호출한 사실이나 제목만 있는 작업 목록은 상세 계획을 대신하지 않는다.

## 계획을 만드는 순서

1. 기존 사용자 요청·확정된 결정·남은 질문·기존 작업을 확인한다. 해결되지 않은 제품 정책을 임의로 제외하지 않는다.
2. 메인이 요청 전체를 주요 단계로 나누고 `Tasks.register_execution_plan`에 작업·수용 기준·의존 관계를 등록한다. 단계 수를 늘려 진행률을 부풀리지 않는다.
3. 메인은 직접 수행할 범위와 위임할 범위를 정한다. 위임에는 전체 목표, 파일 소유권, 입력, 제외 범위, 반환 조건을 전달한다. 독립 실행의 실익이 없는 작업은 직접 수행한다.
4. 담당자는 구현 전에 상세 계획을 반환한다. 각 단계에 고유 ID, 수행 행동, 완료 조건, 입력, 출력, 검증 방법을 작성한다. 메인은 전체 계획과 연결·충돌·누락을 확인한 후 원장에 등록한다.
5. 착수 점검을 통과한 범위만 실행한다. 계획을 변경하면 이유와 영향·재검증을 기록한다. 사후 등록을 사전 계획으로 표시하지 않는다.

계획의 `owner`는 작업 원장의 역할 값이다. 에이전트의 별명이나 프로세스 식별자가 아니다. 위임받은 담당자가 만든 계획을 메인이 원장에 등록할 수 있지만 작성 주체·원본 응답·등록 시점을 실제와 다르게 기록하지 않는다.

## 사람에게 물어야 하는 경우

제품의 핵심 동작·범위·데이터 공유·인증·데이터 소유권·보존/이전·기존 서버 사용 여부처럼 사용자 결정이 필요한 내용은 기존 근거를 먼저 찾는다. 근거가 없으면 추천안과 대안의 영향을 묶어서 질문한다. 작업자가 판단할 수 있는 가역적인 구현 세부 사항은 기존 위임 범위 안에서 결정하고 근거를 남긴다.

질문을 보내기 전에 필수 여부와 영향 작업을 정한다. 필수 질문은 원장에 먼저 열고 해당 작업 및 의존 후속 작업을 대기시킨다. 관계없는 작업은 계속할 수 있다. 질문을 단지 진행 메시지에 적는 것으로 실행 차단이 등록되지는 않는다.

응답 부재·시간 경과·작업자의 추측·동일한 선택을 구현한 사실은 답변이 아니다. 실제 사용자 답변의 출처를 확인하고 질문에 연결한 뒤에만 대기를 해제한다. 선택이 모호하거나 여러 질문에 동시에 대응하면 확인 전 대기를 유지한다. 자유문을 기계적으로 의미 해석해 승인으로 승격하지 않는다. 사람이 내부 식별자나 검증용 토큰을 직접 입력하도록 요구하지 않는다.

## 적용과 이력

`Tasks.configure_execution_policy(root_session_path, root_session_id, ...)`로 정책을 활성화하고, `Tasks.configure_task_plan(task_id, work_plan, reason)`으로 담당 계획을 등록한다. 정책의 적용 작업 종류는 명시하며, 기존 완료 점검 설정과 별개의 계약이다. 계획 예시는 다음과 같다.

다음 실행에서는 `Tasks.bind_execution_session(root_session_path, root_session_id)`로 해당 실행의 메인 원본을 명시 연결한다. 기존 실행의 연결을 바꾸거나 정책을 약화하지 않는다. 기존 작업을 새 실행에서 재시도할 때도 새 실행의 전체 계획 연결과 담당 계획 등록을 다시 확인한다.

최초 실행은 `task --operation configure-execution-policy`로 정책과 원본 세션을 먼저 고정한다. 정책이 없는 상태에서 `bind-execution-session`을 호출하지 않는다. 정책 설정은 한 번이며 이후 실행만 별도 바인딩한다. 전체 계획 소속과 담당 상세 계획은 별도다. `configure-qa`만으로 QA 담당 계획이 생기지 않으므로 QA도 dispatch 전에 원장 역할·해결된 전체 계획 작업 ID로 `configure-task-plan`을 등록한다.

### 이미 시작한 전체 계획에 단계 추가

새 단계는 `task --operation revise-execution-plan`의 `added_steps`로 등록한다. 먼저 `register`로 만든 단계가 있다면 다시 등록하지 않고 `existing_task_ids`에 정확한 ID를 지정한다. 변경 이유와 실제 로컬 근거 파일을 함께 남긴다.

```json
{
  "added_steps": [],
  "existing_task_ids": ["DESIGN-STAGE", "DEVELOPMENT-PLAN-STAGE"],
  "reason": "필요한 후속 검토 단계를 전체 계획에 명시적으로 추가",
  "evidence": "docs/stage-change.md"
}
```

```sh
rtk proxy python3 .kmp-agent/agent.py task --run-id RUN --operation revise-execution-plan --data docs/guard-inputs/plan-revision.json
```

연결 대상은 같은 프로젝트·작업 종류의 미착수 TODO/READY/BLOCKED 작업이어야 한다. 시작 이력·다른 전체 계획 소속·EXCLUDED·중복 ID는 거절한다. 신규·기존 추가 중 하나라도 부적합하면 전체 변경을 저장하지 않는다. 과거 순서·변경 근거는 보존하며 사후 연결을 사전 등록으로 표시하지 않는다. 이후 각 단계의 `configure-task-plan`, 문서/기술 계약, `ready`·`begin`은 그대로 필요하다. 계획 연결은 착수나 승인이 아니다.

이 추가 단계 연결 경로는 [v0.4.6 지원 범위](releases/v0.4.6.md)에 포함된다. v0.4.5 설치본에는 소급 적용되지 않으며 v0.4.6 또는 수정 코드가 포함된 전체 SHA를 명시 선택해야 한다.

### 담당 상세 계획 예시

```json
{
  "version": 1,
  "owner": "development",
  "whole_plan_task_id": "IMPLEMENT",
  "steps": [{
    "id": "S1",
    "action": "입력 계약 검증과 오류 응답을 구현한다",
    "completion_criteria": ["빈 입력을 명시적으로 거부한다"],
    "inputs": ["docs/requirements.md"],
    "outputs": ["검증 구현과 회귀 시험"],
    "verification": ["정상 입력과 빈 입력의 기대 결과를 검사한다"]
  }],
  "completion_criteria": ["요구사항에 맞는 오류 응답과 정상 동작"],
  "inputs": ["docs/requirements.md"],
  "outputs": ["검증 구현과 회귀 시험"],
  "verification": ["관련 회귀 시험 실행"]
}
```

`whole_plan_task_id`는 현재 실행 계획의 실제 작업을 가리킨다. 예제의 역할·작업 ID는 제품의 실제 원장 값으로 맞춘다. 문자열과 목록은 비어 있을 수 없으며 단계 ID는 중복할 수 없다.

`Tasks.open_question(question_id, question, affected_task_ids, options=..., ...)`으로 필수 질문을 등록한다. 선택지는 내부 ID와 사람이 읽는 `label`을 가진다. `Tasks.answer_question(...)`에는 실제 native 답변과 그 사용자 입력 기록의 ordinal·payload SHA-256을 전달한다. 임의로 만든 답변 텍스트를 전달하는 승인 API가 아니다. `Tasks.question_status()`는 같은 원장의 질문 상태를 조회한다.

typed 승인 질문의 필수 ID는 `approve`이며 질문 표시 전에 검사한다. UI 표시 질문의 줄바꿈·512바이트 절단과 원래 전체 질문을 구분하고, 실제 호출 ID·항목·선택지·동결 계약을 검증한다. 이미 받은 원문은 `task --operation recover-question`의 명시적 근거로 복구할 수 있다. 선택지 ID 치환·범위 변경·자유문 승인 승격은 허용하지 않는다. 스키마·감사 이력·구버전의 잘못된 ID 제한은 [승인 처리와 복구](approval-authority.md#이미-받은-응답의-명시적-복구)를 따른다. 이 보완은 [v0.4.7 지원 범위](releases/v0.4.7.md)에 포함되며 기존 v0.4.6에 소급되지 않는다.

CLI는 `tasks configure-execution-policy`, `tasks configure-task-plan`, `tasks open-question`, `tasks answer-question`, `tasks question-status`와 이름 있는 인자의 `--data` JSON을 사용한다. 실제 root native 세션의 절대경로와 UUID는 프로젝트 로컬에만 보관하고 공통 PR·합성 예제에는 넣지 않는다.

새 실행의 연결 명령은 `tasks bind-execution-session`이다. 현재 자동 해제 경로는 명시 선택형 답변이다. `FREEFORM`은 실제 수신 원문을 보존하지만 의미를 자동 승인하지 않고 OPEN을 유지한다. 자유문 대기를 별도 확인으로 해제하는 API는 지원하지 않으므로, 해제가 필요한 필수 질문은 사람이 읽는 명시 선택형으로 구성한다.

실행 정책은 명시적으로 활성화하는 프로젝트 계약이다. 활성화 전의 완료 이력은 보존한다. 기존 활성 시도에 대한 이행 예외와 새 시도의 엄격한 적용을 구분하며, 작업 ID 자체를 영구 면제하지 않는다. 새 필수 질문은 기존 활성 시도에도 영향을 줄 수 있다.

필수 답변 원본은 활성화 때 고정한 메인 native 세션에서 검증한다. 임의의 `role=user` 이벤트·작업자의 문서·다른 세션·과거 답변을 실제 새 답변으로 취급하지 않는다. 확인할 수 없는 출처는 미확인으로 남긴다. 정책 파일 삭제나 약화로 이미 활성화한 계약을 지우지 않는다.

원장의 착수·재개·제출·검토 및 관리되는 역할 호출 경로가 집행 범위다. 관리되는 실행 중 질문이 열리면 해당 소유 프로세스의 중단·상태 처리를 확인한다. 이미 발생한 외부 부수 효과를 되돌리는 기능이나 임의의 셸·운영체제 전체를 차단하는 기능으로 표현하지 않는다.

대시보드와 CMD는 같은 작업 원장과 질문 상태를 읽는다. 계획 등록, 착수 허용 여부, 필요한 답변, 차단 이유를 별도 진행표로 추측하지 않는다. 완료 판정에는 기존 [완료 점검](completion-checks.md)도 그대로 적용한다.
