# 프로젝트 결정과 단계별 개발 계약

개별 제품의 기술을 선택하는 규격이 아니다. 제품별 기존 지침·기술 결정 문서를 원본으로 유지하고 [설정 템플릿](templates/project-settings.json)의 value/reason에 결정이나 원본 참조를 연결한다. 설정은 제품 문서 옆에 한 벌만 두고 기능 문서에 복제하지 않는다. 실제 구현 타깃은 디자인 타깃과 별개다.

상태는 CONFIRMED(확정), PROPOSED(제안), UNDECIDED(미정), NOT_APPLICABLE(해당 없음)이다. 해당 없음에도 이유가 필요하다. 제안은 착수 승인으로 취급하지 않는다. implementation_targets의 확정 value는 선택한 실제 타깃 ID 배열이다. UI 기술·버전·지원 범위·공유 로직/UI와 플랫폼별 책임·소유 모듈을 타깃별로 명시한다. 웹 기술이나 KMP UI 공유를 자동 채택하지 않는다.

server_mode는 none / existing / new다. none이면 서버 기술·DB·API·정책 책임·마이그레이션을 해당 없음으로 적는다. existing은 API와 정책 책임을 확인하고 소유하지 않는 서버 내부 기술·DB·마이그레이션은 해당 없음과 경계를 기록할 수 있다. new는 이를 새로 결정한다. api_contract의 mode는 real / temporary / mock이다. 임시 계약·목 데이터는 산출물에도 표시하고 실제 연동으로 보고하지 않는다.

## 설정 책임과 미구현 인터페이스

제품 목표·기능·스택·기획/디자인 원본·인수 조건·실행/테스트 명령은 적용 프로젝트가 정한다. 기존 설정과 연결 문서를 해당 프로젝트에 보관하며 공통 하네스에 제품 정책을 옮기지 않는다. 현재 스키마는 기술·API·정책·실행 안내·인수 조건의 참조와 단계별 근거를 동결하는 범위다. runbook 문서의 명령 참조가 자동 테스트 실행기를 뜻하지 않는다.

목표 흐름은 사용자의 매번 별도 요청 없이 확정된 기획·디자인 변경을 감지·분석·구현 수정·재검증하는 것이다. 감시 대상과 변경 확정 조건은 프로젝트가 정한다. 이 설정 인터페이스·상시 감시·의미상 영향 분석·자동 수정/재검증은 PLANNED다. 현재 project-settings.json에 미지원 감시 키를 추가해 실행 가능한 설정처럼 사용하지 않는다. 결정 기록은 기존 프로젝트 문서에서 유지하고 구현 시 정식 스키마를 별도로 검토한다.

## 단계별 필수 입력

| 단계 ID | 확정되어야 할 입력 | 진행에 영향 없는 미정 |
| --- | --- | --- |
| ui | 구현 타깃·UI 기술·지원 범위·코드 공유/소유 모듈 | API·서버·DB 미정이어도 목 UI 가능 |
| client_integration | 구현 타깃·코드 책임·서버 모드(existing/new)·real API·정책 책임 | 신규 서버 기술·DB 미정은 계약 기반 클라이언트 작업을 막지 않음 |
| server_implementation | 코드 책임·서버 모드(new)·서버 기술·DB·마이그레이션 계획·real API·정책 책임 | UI 기술·지원 OS 미정은 서버 작업을 막지 않음 |
| integration_verification | UI 단계 입력·서버 모드·실행 안내·전체 연결 수용 기준. existing/new는 real API·정책, new는 서버·DB·마이그레이션도 필요 | none의 서버/API/DB 검증은 해당 없음; 로컬 기능 검증만 |

없는 서버에 연동/서버 구현 작업을 만들지 않는다. 기존 서버 연동에 신규 서버 개발 단계를 요구하지 않는다. 해당 작업만 READY/인계를 거절하며 기존 의존성·시안 검토·반환·재시도·재개 규칙도 유지한다. 관련 없는 작업을 선행 의존성으로 묶어 전체를 차단하지 않는다.

## 실행·갱신

기존 task 등록 뒤 `configure-stage`를 호출한다. `--data` JSON은 `{"task_id":"<기존 ID>","stage":"ui","settings":"<제품 경로>/project-settings.json"}` 형식이다.

```sh
rtk proxy python3 harness/tasks.py --run-id <기존-run-id> configure-stage --data <작업-설정.json>
```

설정과 연결 문서는 기존 inputs·불변 artifact snapshot에 저장하고 tasks.yaml의 stage_contract에서 참조한다. 기존 역할 컨텍스트와 입력 수신 해시에 포함하며 별도 버전/상태 DB를 만들지 않는다. ready·begin·handoff와 통합 review를 검사한다. 미정 해소 시 비활성 TODO/BLOCKED 작업만 재구성하고 기존 ready 흐름을 따른다. 기존 실행 입력·검토는 유지한다. 원본 파일만 고쳐 동결 입력을 바꿀 수 없다.

기존 기획·디자인/입력 해석 시험은 원래 계약을 유지한다. **실제 개발 작업 배정에는 단계 설정을 필수로 지정한다.** 자동 단계 추론이나 전체 제품의 자동 설정 전파는 구현하지 않았다.

## 개발·검증 산출물

[개발 계획](templates/development-plan.md)은 설정·API·정책·실행 안내·검증 기준 원본을 참조한다. API 계약에 버전·요청/응답·오류·인증·정책 ID별 클라이언트의 입력/표시 책임과 서버의 최종 검증·권한·저장 책임·오류/재시도 처리를 명시한다. 서버 없음은 로컬 정책 소유를 기록한다.

실행 안내에 타깃/서버 실행 명령·작업 디렉터리·실행 순서·환경변수 **이름과 자리표시자**·DB 준비/마이그레이션/실패 복구·격리된 시험 데이터 초기화 절차를 적는다. 비밀값·실제 접속 자격 증명은 입력/로그에 기록하지 않는다. 기존 마스킹이 이를 대신 보장한다고 가정하지 않는다.

통합 검증의 필수 기준별 PASS evidence JSON은 mode=real, result=PASS, tested_outputs={출력 경로:SHA}, target_results={모든 선택 타깃:PASS}, end_to_end=PASS, environment, observations를 요구한다. 검증 기록이 공식 원본이며 명세에 복제하지 않는다. 이는 증거 정합성 검사이며 API·DB 자동 실행 엔진이 아니다. 검토자가 관측·실행 근거를 확인한다. 목/실제·native/browser·개별/전체 연결을 구분하고 미실행은 NOT_RUN으로 남긴다.

제품 검증 시나리오·테스트 명령·목표치는 적용 프로젝트에서 정의한다. 예를 들어 신규 서버가 있는 프로젝트는 생성→API 저장→재조회·실패 처리 등을 자신의 인수 조건으로 정할 수 있다. 메모 예제나 신규 서버 구성을 공통 하네스의 제품 목표·구현 계획으로 채택하지 않는다.

개발 구현의 기준·코드·검증 상태는 [개발 추적](development-tracking.md)의 공통 게이트에서 기존 입력으로 자동 연결하거나 누락을 차단한다. 명시 설정에는 configure-development를 사용한다. 입력 해석 예제에는 소급 적용하지 않는다.
