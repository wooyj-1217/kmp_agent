# 대상 프로젝트 연결·반영 검증

기준 구현은 [projects.py](../harness/projects.py)다. 일반 제품의 진입 절차는 [특정 버전 설치·init·update](installation.md)이며, 이 문서는 선택한 설치 버전 안의 연결 점검 구현과 개발용 원본 참조를 설명한다. 제품별 목표·정책·산출물·작업·로그는 대상 저장소에 유지한다. 이 도구는 모델을 호출하거나 원본 세션을 sync하지 않으며, 실제 훅 호출 근거를 읽어 판정한다.

## 대상 설정과 실행

개발용 로컬 참조 대상은 `.harness/projects.json`에 등록할 수 있다(Git 제외). 상대 경로는 실행 도구 루트를 기준으로 한다. 다른 환경에서는 `--config <JSON>` 또는 `--target <저장소 루트>`를 사용할 수 있다. 일반 설치 대상에는 `.kmp-agent/project.json`과 프로젝트 진입 명령을 사용하며 원본 작업 트리의 버전을 자동 배포하지 않는다.

```json
{"targets": [{"path": "../kmp_agent_demo_app", "skills": []}]}
```

skills에는 공통 `.agents/skills/<이름>/SKILL.md`가 존재하는 스킬만 명시한다. 선택하지 않은 스킬은 설치하지 않는다. 현재 공통 스킬이 없는 데모의 skills는 빈 배열이며 N/A다. 외부 설치 스킬이나 개인 설정을 공통 스킬로 복제하지 않는다.

```sh
rtk proxy python3 harness/projects.py apply --config .harness/projects.json
rtk proxy python3 harness/projects.py check --config .harness/projects.json
rtk proxy python3 harness/projects.py verify --target ../kmp_agent_demo_app --session-id <실제 세션 ID> --message-id <실제 메시지 ID>
```

apply는 필요한 연결 설정만 갱신하고 현재 증거로 검증한다. check/verify는 대상 설정·이벤트·원본을 수정하지 않는다. 종료 코드 0은 모든 지정 대상의 VERIFIED만 의미한다. 설정 쓰기가 성공했어도 실제 검증 대기·재시작 필요·실패이면 1이다. JSON의 connection과 runtime 결과를 따로 읽는다.

## 변경별 반영

| 변경 | 반영 경로 | 완료 판단 |
| --- | --- | --- |
| 공통 Python 코드 | 선택한 설치 버전(개발 모드는 원본)의 파일을 실행. 다른 버전은 명시적 update 전까지 사용하지 않음 | 현재 코드 묶음 해시로 실제 요청 수집 확인. 개발 코드만 변경됐다면 다음 요청 대기이며 재시작을 강제하지 않음 |
| 역할 지침·템플릿 등 공통 문서 | 선택 버전의 문서를 참조; 필요한 역할 문서만 읽음 | 변경 해시를 감지하고 새 세션 필요로 표시. 모든 문서를 읽었다는 의미가 아닌 새 시작 입력의 가용 버전임 |
| 선택한 공통 스킬 | 대상 `.agents/skills/<이름>`의 상대 심볼릭 링크 | 내용·선택 변경 시 새 세션 필요. 같은 이름의 제품 스킬은 보존하고 충돌 보고 |
| 공통 수집 훅 | 설치 모드는 개인 경로 없는 고정 프로젝트 진입 파일로 연결. 직접 참조 개발 모드는 원본의 두 수집 핸들러만 병합 | 정의 변경 시 대상 `/hooks` 검토·신뢰와 새 세션 필요. 설치 버전 변경만으로 고정 훅 명령을 변경하지 않음 |
| 연결 설정·제품 시작 설정 | 대상 경로·선택 스킬·관리 AGENTS 블록·두 수집 훅을 점검. 제품 `.codex/config.toml`은 해시 변경을 감지하되 원문·값을 복사/수정하지 않음 | 시작 입력이 바뀌면 새 세션 필요. 개인·플랫폼별 일반 Codex 설정은 자동 배포 범위 밖이며 제품 설정으로 유지 |

관리 범위는 AGENTS.md의 `kmp-agent:begin/end` 블록, 공용 수집 스크립트 핸들러, 필요한 Git 제외 항목, 명시한 스킬 링크와 `.harness/integration*.json`이다. 프로젝트 식별·경로는 [설치 연결 설정](installation.md#프로젝트-식별검증-범위)이 기준이다. 결과에는 실제 대상 project_id·verification_scope를 자동 연결하며 식별할 수 없으면 PROJECT_ID_UNKNOWN/NOT_RUN과 원인을 표시한다. 기존 문서·다른 훅·설정 키·산출물·로그는 보존한다. 손상된 관리 블록·중복 핸들러·다른 스킬 경로와의 충돌은 임의 정리하지 않고 실패·복구 방법을 보고한다. 선택 해제된 스킬도 직접 만든 링크만 제거하며 제품 파일로 교체돼 있으면 보존한다. 잠금·원자적 저장·수정 전 해시 재확인으로 중복 실행과 동시 편집 충돌을 방어한다.

## 자동 실행과 상태 파일

- 하네스의 신뢰된 Stop 훅은 등록 대상을 **읽기 점검**하고 `.harness/projects-status.json`에 상태를 기록한다. 대상 설정·설치 버전을 자동 변경하지 않는다.
- 대상의 신뢰된 수신·Stop 훅은 공용 코드를 실행하고 원문 수집 후 대상 `.harness/integration-status.json`을 갱신한다. 연결 기준·시작 입력 기준 시각은 대상 `.harness/integration.json`에 둔다. 저장 대상은 스크립트 위치가 아니라 호출 저장소다.
- 설치 대상은 명시적 init/update에서만 연결 설정을 갱신한다. 개발 모드에서도 명시적인 apply를 사용하며 원본 변경만으로 대상에 쓰지 않는다. 대상 쓰기 권한이 없으면 실패를 보고하며 권한을 우회하지 않는다.
- 파일 감시 데몬은 없다. 훅이 없는 편집기·중단·강제 종료 뒤에는 다음 정상 훅 또는 위 명령이 필요하다. 읽기 전용 check는 저장된 과거 PASS만 보여주지 않고 현재 원본 해시와 다시 대조한다. 대상에서 갱신한 최신 결과는 하네스의 check로 바로 조회할 수 있다.

## 실제 동작 판정과 복구

내부 합성 테스트와 대상 실제 검증은 분리한다. 대상 PASS에는 **현재 공통 코드/시작 입력 해시**, 해당 버전 적용 이후 생성한 세션, 동일 턴의 수신·Stop 훅 성공, 대상 경로로 향한 sync, 수신 또는 Stop 호출 시간 안에 수집된 실제 사용자 원문 정확히 1건이 필요하다. 이벤트·메시지·세션·호출 ID와 근거 줄을 보고한다. 환경·지침 메시지를 일반 사용자 요청으로 사용하지 않는다. 수동 sync로 앞서 가져온 메시지는 이 PASS를 충족하지 않는다.

| 상태 | 의미·복구 |
| --- | --- |
| VERIFIED / PASS | 현재 버전의 해당 대상·세션·요청에 대한 실제 수집 확인 |
| CONFIG_DRIFT / NOT_CONFIGURED | apply 실행. 관리 영역 외 설정은 유지 |
| RESTART_REQUIRED | 지침·스킬·설정 변경 또는 새 시작 근거 부족. apply 후 `rtk proxy codex --no-daemon --cd <대상>` 등으로 새 세션 시작. 이전 스레드 재개만으로 시작 지침 갱신을 증명하지 않음 |
| AWAITING_HOOK | 대상 `/hooks`의 설정 탐색·신뢰·활성 상태와 호출 진단 확인. 훅 정의가 바뀌면 사용자 신뢰 필요 |
| AWAITING_REQUEST | 새 코드의 다음 일반 요청 또는 현재 요청의 Stop 수집 대기. 수동 sync 금지 |
| HOOK_FAILED / VERIFICATION_FAILED / FAILED | 대상 진단의 오류·중복 메시지·잘못된 저장 경로·권한·설정/소유 충돌 확인 후 재시도. 과거 PASS로 덮어 숨기지 않음 |

정확한 기존 세션의 메모리 내 설정 목록은 이 도구가 조회하지 않는다. 오래된 세션·시작 시각 UNKNOWN은 보수적으로 재시작 필요로 남긴다. 원문 자동 수집 PASS는 역할 수행·지침 준수·제품 품질·사용자 개입 분류 연결까지 검증한 결과가 아니다. 토큰·시간·로그의 원본·마스킹·Git 제외 규칙은 [기존 로깅](harness-logging.md)을 따른다.
