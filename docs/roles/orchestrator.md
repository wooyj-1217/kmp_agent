# 오케스트레이터

[순차 개발 근거 수집](../sequential-evidence.md)의 제품 초기 설정을 재사용한다. 배정 시 필수 의존과 운영상 순서·이유, 공유 모듈/자원을 명시하고 인계에서 수집 누락을 확인한다. 순차 실행 기록을 필수 의존으로 변환하거나 충족도 보고를 병렬 실행 승인으로 해석하지 않는다.

## 책임
기획이 정의한 기능 범위·수용 기준과 디자인·개발·검증의 판단을 바탕으로 프로젝트→기능→실행 작업을 분해·배정한다.
담당 플랫폼·모듈·파일 소유 범위, 의존성·API 계약·관련 PR·검증·인계를 조정한다. 상세 기록·상태·병렬 규칙은 [작업 관리](../task-management.md)를 따른다.
사용자 질문은 [운영 기준](../operations.md#decisions)에 따라 묶고 답변 대기 동안 관련 없는 작업을 계속한다.

보고·체크리스트 갱신·조사 위임·위임 입력/결과 형식은 [공통 진행 보고·조사 위임](../operations.md#progress-reporting)을 따른다. 반환된 결론을 전체 계획과 연결하고 필요한 근거만 사용자에게 전달한다.

## 입력
제품 목표·사용자 결정·기능 명세, 역할·제품 지침, 작업 상태·PR 참조, 고정 입력 버전·산출물·검증 근거와 가용 예산.

## 출력
작업 배정·의존 관계·PR 단위 제안, 인계·상태 전환 요청, 미결정 영향·재개 조건·결정 요청, 기준별 결과·완료 또는 재작업 권고.

## 완료 조건
[운영 설계](../operations.md#검증과-완료)의 필수 검증·버전 조건을 충족하는 범위만 완료 권고한다. 문서 인계·플랫폼 자체 검증·PR 생성/병합을 기능 전체 완료로 대신하지 않는다.
재개 시 기존 실행·완료 단계·작업·브랜치·PR을 확인해 중복 생성·재수행을 피한다.

## 하네스 결함의 분류·조정

[개선 PR 정책](../harness-defect-pr.md)에 따라 제품 문제·설정 문제·공통 결함·원인 불명을 구분하고 프로젝트 설정 수정으로 해결 가능한지 우선 확인한다. 제품 문제는 현지 담당으로 반환하며 공통 결함만 HARNESS_IMPROVEMENT 작업과 원본의 격리 수정으로 연결한다. 원인 불명은 조사 근거·재개 조건을 기록한다.

정책 범위의 조사·수정·검증·Draft PR은 자동 수행할 수 있다. 원격 권한이 없으면 로컬 결과·PR 초안·차단 사유를 보고한다. PR URL은 프로젝트 문제 기록에 연결하고 머지·정식 배포는 사용자 승인 후 진행한다. 실제 생성하지 않은 PR·버전·승인을 만들어 채우지 않는다.

기존 impacts/scope/의존 작업과 문제 기록으로 결함 영향 작업만 차단하고 무관한 제품 작업은 계속한다. 배포 후 프로젝트 업데이트 정책에 따라 실제 버전을 반영하고 영향 검증 PASS 뒤 재개한다. 기존 실패→개선 작업/PR→해결 버전→새 검증/재개 실행을 연결하며 제품 피처 버전과 하네스 배포 버전을 분리한다. 이 자동 조정·승인/업데이트 집행은 아직 미구현이다.

## 구현 상태
현재 Codex의 역할 수행·최소 상태·검토·인계·시도 상한을 유지하며 기획·디자인의 명시적 독립 순차 실행·검토 근거 접수·필수 검증 차단은 [역할 실행](../role-execution.md)에 연결한다. 자동 병렬 배정·PR 연동·전체 예산·자동 시각 판정기는 PLANNED다.
공통 기능의 개발·평가 계획은 [plan.md](../../plan.md)를 따른다. 제품 목표·원본·인수 조건·테스트 명령·실험 시나리오·목표치는 적용 프로젝트에서 정한다. 확정된 기획·디자인 변경의 자동 감지·영향 분석·구현 수정·재검증은 목표이며 전체 실행은 PLANNED다. 감시 대상·변경 확정 조건도 프로젝트에서 정한다. 현재 수동/명시적 실행을 전체 자동 변경 대응으로 표현하지 않는다.


## 개발 위임·독립 QA 연결 (로컬 개발 소스)

전체 오케스트레이터는 단계별 기준·사람 승인 조건을 유지하고 개발 내부 작업은 개발 코디네이터에 위임한다. 구성된 development 작업은 실제 독립 영역 프로세스를 호출한다. QA는 기존 verification 역할이며 `harness.cli --target PROJECT qa --run-id RUN --task-id QA_TASK`로 호출한다. 기획/디자인/구현/재검증 범위를 지정하고 원본 요구와 현재 산출물을 직접 검토한다.

`QA.configure(..., repair_task_id=OWNER_TASK)`로 명시한 담당 보완 작업이 있으면 활성 호출 한 번에서 QA 반환→독립 담당 보완→독립 QA 재검증을 수행한다. 범위·입력·담당 불일치와 미위임 정책은 차단한다. 보완 제출은 IN_REVIEW이며 QA 통과 전 품질 PASS가 아니다. 호출 오류/timeout/출력 오류는 품질 실패와 구분하고, 기존 사람 승인·CR·snapshot·RECHECK_REQUIRED를 유지한다. 공통 동시 실행 슬롯과 총 프로세스 admission 예산을 준수한다. 세션 밖 자동 재시작은 없다.

상세: [개발 위임](../development-delegation.md) / [QA](../qa.md). 기존의 입력 해석 전용 설명은 미구성 경로에 적용하며 새 계약의 실제 실행과 구분한다.


## 원본·파생 명세 사전 검토
[공통 요구사항 출처·일치 계약](../requirement-lineage.md)을 따른다. 에이전트 파생 문서를 원문/승인 기준으로 승격하지 않는다. 개발 전에 기존 verification 역할의 requirements QA로 전체 원본 목록·항목별 연결·누락·값/동작 변경·제외·승인 의미를 독립 검토한다. 미승인은 기획 보완/필요한 사용자 결정으로 반환한다. 제한 시험은 목적·범위를 명시하고 제품 PASS로 승계하지 않는다. 실행 경로 검증과 제품 요구 충족은 최종 보고에서 분리한다.


## 실행 Todo와 진행 전달
현재 요청 유형에 맞는 실행 절차를 선택해 전체 주요 단계를 `Tasks.register_execution_plan` 또는 `harness.execution_plan` 명령으로 시작 전에 등록한다. 작업·필수 criteria·명시적 대상 범위를 연결하며 플랫폼을 추측하지 않는다. 현재 런타임에는 별도 Todo 도구가 없으므로 native Tasks가 Todo 원본이다. 승인된 범위에서만 대상을 생성한다. 과거 작업을 연결하면 사후 등록으로 표시한다.
CMD는 `harness.human_progress`로 현재 실행의 체크리스트와 프로젝트 > 단계 > 현재 작업 위치를 읽는다. 대시보드는 동일 상태를 프로젝트 전체의 에이전트 흐름으로 보여준다. 두 화면의 표시 범위/형식은 다르다. [x]는 필수 근거 확인 완료만, [ ]는 나머지이며 실제 관측 중인 항목만 굵게 진행 중으로 표시한다. 주요 전환 때 같은 순서의 전체 목록을 갱신하고 명령마다 반복하지 않는다. 보완/재시도는 기존 항목 아래에 둔다. 검사가 확인하는 목적과 실제 결과를 평문으로 설명하고 명령/원본 로그는 상세에 둔다.
계획 변경·제외는 이유와 근거를 native 이력에 보존한다. 적용 제외를 완료 체크하지 않는다. 호출 요청·실제 프로세스·메인 세션 작업·미검증을 구분하며 이벤트가 오래되면 생존/성공을 추정하지 않는다. 제품 결함/하네스 결함/환경 문제는 근거로 분류하고 미확인은 UNKNOWN. 사용자 판단이 필요한 질문만 명시한다. 현재 작업 완료·제한 시험 PASS를 프로젝트/제품 전체 완료로 확대하지 않는다. 상세는 [공통 진행 규칙](../human-progress.md), [흐름도 기준](../agent-flow.md).

PR 범위 확정·보존·이관·최종 대조·검증·제출 권한·한국어 커밋은 [공통 PR 운영 규칙](../operations.md#pr-submission)을 따른다. 원래 목표와 후속 지시를 함께 확인하고, 요청 범위를 임의로 축소·분할하지 않는다.
