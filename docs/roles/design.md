# 디자인 역할

## 책임
제품별 입력을 구현 가능한 명세와 시안으로 구체화한다.
업무 정책 누락·모순은 기획으로 반환한다. 시각적 선택은 역할 재량에서 제안하고 가정·근거를 기록한다. 사용자 의도·핵심 정책의 확인은 [공통 질문 규칙](../operations.md#decisions)을 따른다.

## 정보 그룹·일관성·시각적 우선순위

핵심 책임「요구사항을 구현 가능한 명세와 실제로 검토할 수 있는 시안으로 구체화한다」를 유지하며 아래 게슈탈트 원칙으로 설계·비교·시각 검토를 보완한다. 수치·스타일을 일률적으로 강제하지 않고 화면 목적·콘텐츠·플랫폼·접근성에 맞춰 적용한다.

- **근접성**: 사용자 관점에서 의미가 연결된 정보와 행동을 묶고 그룹 내부 간격과 그룹 사이 간격을 구분한다. 제목·설명·입력·오류·관련 버튼의 소속을 명확히 한다. 공간이 남는다는 이유로 관련 요소를 멀리 떨어뜨리지 않으며 모든 그룹을 테두리 카드로 감싸는 방식에 의존하지 않는다.
- **유사성**: 같은 역할의 버튼·상태·카드·텍스트에는 같은 시각 표현을 사용한다. 다른 의미를 같은 강조색·모양으로 표현해 혼동시키거나 장식 목적으로 역할마다 다른 색을 부여하지 않는다. 색상만으로 상태·구분을 전달하지 않는다. 기존 디자인 시스템과 선택된 방향을 우선 재사용한다.
- **전경과 배경**: 사용자 목표에 따라 정보·행동의 우선순위를 정하고 크기·위치·여백·명도 대비·타이포로 위계를 만든다. 현재 작업·주요 행동·해결할 오류를 적절히 강조하고 보조 정보·기술 상세는 우선순위를 낮추거나 펼쳐보기로 제공한다. 모든 요소를 동시에 강조하지 않으며 보조 텍스트도 읽을 수 있는 대비를 유지한다.

## 입력
제품별 요구사항·인계 기준 버전, 목표 플랫폼·기술 제약·디자인 규칙, 사용자 결정과 참고 자료를 받는다.

## 진행 흐름
요구사항·레퍼런스 → 최소 디자인 토큰 → 대표 화면 시안 비교 → 사용자 방향 선택 → 필요한 컴포넌트 → 전체 화면·상태 → 브라우저 검증 순서로 진행한다. 별도 실행기나 상태 체계를 만들지 않고 기존 작업·산출물·검토 기록에 연결한다.

시안 제작 전에 화면별 사용자 목표·가장 먼저 알아야 할 정보·주요 행동·함께 묶을 정보·상세로 내려도 되는 정보를 정리한다.

1. 레퍼런스의 출처·대응 화면·적용 이유를 기록한다. 자료가 없거나 일부만 대응하면 부족한 근거와 요구사항 기반 가정을 명시하며 관련 없는 자료로 개수를 채우지 않는다.
2. 대표 화면에 필요한 색상·타이포·간격·크기의 최소 토큰부터 정의하고 CSS 변수에 연결한다. 명세에는 이름·값·단위·CSS 변수·사용 범위를 기록하며 전체 라이브러리를 미리 만들지 않는다.
3. 방향이 미정이면 같은 SCREEN ID·콘텐츠·상태·화면 크기로 HTML/CSS 시안 2~3개를 비교한다. 안별 경로/버전으로 구분하고 정보 그룹·배치·밀도·시각적 위계와 타이포 차이 및 근거·장단점을 제시한다. 색상만 바꾸거나 원칙 이름만 붙인 안은 비교안으로 삼지 않는다.
4. 실제 시안과 장단점을 제시한 뒤 사용자의 방향 선택·출처·적용 입력 버전을 기록한다. 응답 전 영향받는 확장 작업만 보류한다. 기존 방향 결정은 근거를 확인해 재사용하고 반복 선택을 요구하지 않는다. 요구·방향 변경이 선택에 영향을 주는 경우만 재확인하며 단순 컴포넌트·상태 추가로 재승인을 요구하지 않는다.
5. 선택한 방향으로 실제 화면에서 사용하는 컴포넌트·변형·상태만 만들고 전체 화면·상태·크기로 확장한다. 기존 SCREEN/STATE/ACT·수용 기준 ID를 유지하고 명세·시안 불일치를 해결한다. 정상뿐 아니라 로딩·빈 화면·오류·재시도에서도 그룹 관계와 주요 행동의 일관성을 유지하고 긴 콘텐츠·키보드·작은 화면에서 관계와 위계가 유지되는지 확인한다. 화면별 정보 그룹과 구분 이유·가장 강조한 정보/행동·재사용 규칙과 의도적인 예외를 짧게 기록하며 모든 컴포넌트에 장문의 원칙 설명을 요구하지 않는다.

대표 비교·선택은 시안 제작 과정이며 기존 명세 작성/시안 제작/시각 검토 상태를 대체하지 않는다. 미결정·재검토·인계 버전은 운영 기준을 따른다.

## 출력·공통 산출물 규격 — 기준 문서
기능별 폴더에 다음을 둔다. 제품별 루트 위치는 제품 선정 후 지정한다.

    <기능 폴더>/
      requirements.md
      design.md
      prototype/
        index.html
        <화면명>-harness-<지침 식별자>-<시안 ID>[-rN].html
        필요한 CSS·JavaScript·이미지 파일

design.md의 작성 필드는 [템플릿](../templates/design.md)을 따른다. 제품별 화면·업무 정책·토큰·아키텍처를 공통 하네스 문서에 넣지 않는다.
HTML/CSS 시안은 별도 빌드와 외부 서비스 의존 없이 로컬 브라우저에서 확인할 수 있어야 한다. 외부 CDN·필수 웹폰트·실제 API 없이 필요한 자원을 로컬에 둔다.
HTML/CSS 시안 형식은 실제 웹 제품의 기술 선택이나 웹 구현 완료를 뜻하지 않는다.
JavaScript는 샘플 데이터와 상태 전환을 시연하는 최소 범위만 허용한다. 실행 모델·서비스·요금제는 시안 형식과 별개로 미결정이며 ChatGPT Work·Figma·이미지 생성은 필수가 아니다.

## 시안 버전 추적
비교용 새 시안은 기존 파일을 덮어쓰지 않고 같은 prototype/ 안에서 파일명으로 구분한다. 별도 버전 폴더는 만들지 않는다.

- 커밋된 지침: `<화면명>-harness-<하네스 short SHA>-<시안 ID>.html`. short SHA에 대응하는 전체 커밋도 기록한다. 같은 지침으로 재제작하면 `-r2`, `-r3`처럼 확장자 앞에 revision을 붙이고 기존 파일·ID와 충돌하지 않는지 확인한다.
- 사용 지침 중 미커밋 변경이 있으면 HEAD만 쓰지 않고 `<화면명>-harness-draft-<사용 지침 묶음의 해시>-<시안 ID>[-rN].html`로 표시한다. 실제 적용한 지침·템플릿의 저장소 상대 경로와 파일별 원문 SHA-256을 경로순으로 정렬한 목록에 대해 SHA-256을 산정한다. 목록은 `[경로, 파일 SHA-256]` 배열의 UTF-8 JSON(공백 없는 구분자, 비ASCII 문자 그대로)으로 직렬화한다. 대상 목록·파일별 해시·산정 방식·전체 묶음 해시와 기준 HEAD를 명세에 기록하며 사용하지 않은 파일은 포함하지 않는다.
- HTML 내부 주석 또는 메타데이터에 기획 기준 버전, 하네스 커밋 또는 draft 식별자, 시안 ID·revision, 변경 이유를 기록한다. draft의 대상 목록·해시 근거도 HTML에 포함하거나 고정된 근거 파일로 연결한다.
- 기존 시안이 참조하는 CSS·JS·이미지·폰트 등 의존 파일은 새 비교안 때문에 수정하지 않는다. 변경되는 의존 파일도 같은 폴더에서 버전별 파일명으로 구분하거나 HTML에 포함한다. CSS의 url()·JS에서 읽는 자원 등 간접 의존도 포함해 경로·버전/해시를 기록한다. 변경 없는 자원만 그대로 공유한다.
- 사용자 선택 전 활성 시안, index.html 진입 대상, design.md의 기준 시안 참조를 임의로 교체하지 않는다. 비교안 목록만 추가한다. 선택 후 실제 선택 근거와 기준 참조를 함께 갱신하며 이전 파일·의존 자료는 보존한다. 기존 방향 결정의 재사용은 진행 흐름의 기준을 따른다.

파일명의 하네스 식별자는 적용 지침을 나타내며 시안 자체의 변경 이력·제품 커밋은 제품 저장소 Git으로 관리한다. 파일명·해시만으로 사용자 선택·검증 완료를 증명하지 않으며 자동 커밋을 허용하지 않는다. 기존 시안은 일괄 개명하지 않는다.

## ID·상태 시연
명세와 시안은 같은 SCREEN/STATE/ACT ID를 사용한다. 대응 DOM에 data-screen-id / data-state-id / data-action-id를 표시한다.
필요한 정상·로딩·빈 상태·오류·재시도·비활성 상태를 확인할 수 있어야 한다. 해당 없는 상태는 N/A와 이유를 기록한다.
검토용 상태 선택·샘플 데이터 제어 장치는 제품 UI와 구분하고 사용법에 표시한다. 기준 화면 크기와 크기 변화 대응, 키보드·스크롤·접근성·플랫폼 차이도 명세에 정의한다.
목표 플랫폼에 따라 모바일·데스크톱의 기준 크기·크기 변화 대응을 명시한다. 웹이 대상이면 키보드 탐색·포커스 순서/표시/복귀, 브라우저 뒤로/앞으로·새로고침·직접 진입과 미저장 상태의 처리 및 검증 환경을 정의한다. 업무 정책 미결정은 기획으로 반환하고 해당 동작만 차단한다.
정확한 규격은 design.md에 두며 시안이 이를 따른다. 명세·시안 충돌을 해결한 뒤 인계한다.

## HTML 브라우저 검증
각 검사는 PASS / FAIL / NOT_RUN과 대상 명세·시안 버전, SCREEN/STATE/ACT·수용 기준, 환경·크기·재현 경로·근거를 따로 기록한다. 화면×필요 상태×목표 화면 크기와 긴 본문·오류 문구 등 콘텐츠 사례의 누락을 확인한다. N/A는 이유를 남긴다.

| 구분 | 확인과 근거 |
| --- | --- |
| 구조 검사 | 소스의 로컬 참조·ID·CSS 변수 연결을 확인한다. 실제 브라우저가 있으면 DOM·계산된 스타일·요소 경계·overflow·사용 폰트/토큰 값을 명세와 대조한다. 소스 확인과 실제 DOM 관측 범위를 구분한다. |
| 인터랙션 검사 | 실제 클릭·입력·재시도·비활성·상태 전환·키보드/포커스·해당 탐색을 수행하고 기대/실제·ACT/STATE를 연결한다. 함수·이벤트 핸들러 존재만으로 통과시키지 않는다. |
| 캡처 시각 검토 | 실제 렌더링 캡처의 위계·가독성·정렬·긴 본문·오류 문구·잘림·겹침·스크롤·주요 버튼 접근을 관찰한다. 화면/상태/크기·캡처 경로·버전·관찰 결과를 연결한다. |

### 정보 관계·위계의 실제 렌더링 검토

- 관련 정보와 버튼이 같은 그룹으로 읽히는가?
- 같은 의미가 같은 표현을 사용하고 서로 다른 의미가 비슷하게 보여 혼동되지 않는가?
- 먼저 봐야 할 정보와 다음 행동이 드러나는가?
- 보조 정보가 주요 작업을 가리지 않는가?
- 오류 설명과 복구 행동의 관계가 명확한가?
- 작은 화면·긴 콘텐츠·키보드 표시에서도 그룹 관계와 위계가 유지되는가?

문제는 원칙 이름만 쓰지 않고 구체적 요소·사용자 혼동·화면/상태/크기와 캡처 근거·수정 방향을 남긴다. 예: “재시도 버튼이 오류 설명보다 목록에 가까워 목록 전체를 새로고침하는 버튼으로 오해할 수 있음. 오류 설명 바로 아래로 이동한다.” 관련 요구사항·접근성 기준 위반, 관측된 사용성 문제, 선택 가능한 디자인 제안을 구분하고 심각도·차단 근거를 기록한다. 주관적 취향·개선 제안은 자동 완료 차단 결함으로 취급하지 않는다. 사용성 혼동은 실제 사용자 시험을 하지 않았다면 관찰에 따른 위험 추정임을 명시한다.

규칙 기반 검사와 실제 화면 검토를 구분한다. 간격 수치·원칙 단어의 존재로 시각 PASS를 만들지 않는다. 기준 보완을 검증할 때에는 승인 화면을 교체하지 않고 격리된 대표 사례의 적용 전후를 같은 콘텐츠·상태·크기로 렌더링해 비교한다. 이 비교는 새 방향 선택·제품 승인이나 자동 시각 판정의 증거가 아니다.

Figma 제작·추출은 로컬 HTML/CSS 렌더링과 위 DOM·스타일·캡처 확인으로 대체한다. Figma 노드/변수/프레임 검증기를 그대로 실행하거나 가짜 노드·스냅샷·캡처로 통과시키지 않는다. 단일 캡처나 구조 PASS가 인터랙션·전체 시각 검토를 대체하지 않는다. 환경 또는 도구가 없거나 실행하지 않은 검사는 NOT_RUN이며 자동 검증기는 PLANNED다.
수정 후 영향받는 조합·콘텐츠·인터랙션을 새 버전으로 재검증하고 무관한 완료 검토는 반복하지 않는다. HTML 시안 검증은 실제 KMP 웹 제품·네이티브 UI·서버 연동 검증과 별개다.

## 완료 조건 — 서로 독립된 상태
| 항목 | 완료 조건 |
| --- | --- |
| 명세 작성 | 진행 범위의 구현 규격·동작·수용 기준 연결이 명확하고 필요한 정책이 결정됨 |
| 시안 제작 | 해당 화면·상태·행동을 로컬 브라우저에서 확인할 수 있고 명세와 ID가 일치함 |
| 시각 검토 | 실제 렌더링을 보고 명세 일치·잘림·겹침·스크롤·버튼 접근 가능 여부를 확인하고 환경·화면 크기·버전·판정·근거를 기록함 |

검토 환경 또는 자료가 없으면 시각 검토는 NOT_RUN이다. 파일·명세 존재나 해시 변경은 시각 검토 PASS가 아니다. 명세만 완료됐다고 디자인 전체 완료를 선언하지 않는다.
제품 UI 최종 인계에는 필요한 세 상태의 완료와 불일치 해결 근거가 있어야 한다. 시안이 없어도 가능한 Mock UI·비시각 작업의 제한적 인계는 [개발 역할](development.md)을 따른다. 과거 문서 시험은 제품·시각 품질 완료로 소급하지 않는다.

## 출력·다음 역할 인계
명세·시안 경로와 고정 버전, 기능/작업·수용 기준·화면/상태/행동 연결, 목표 플랫폼·디자인 규칙, 상태 시연 방법·샘플 데이터, 세 진행 상태, 시각 검토·불일치 해결 근거, 미결정·차단 단계·다음 담당을 개발·검증에 전달한다.
버전·차단·변경 이력은 [운영 기준](../operations.md)을 참조한다.

## 구현 상태
독립 순차 프로세스 진입점·컨텍스트·실제 파일 제출·대기/재개·P→D 기준본·검토 접수는 [실행 계약](../role-execution.md)을 따른다. 실제 사용하는 tokens.css·components.html·system.md와 화면 시안이 필수 산출물이다. 기존 자원을 조사해 재사용하며 제출 기준본에 함께 보관한다. 구조·인터랙션·시각 결과를 별도 접수하고 필수 NOT_RUN/FAIL은 DONE을 차단한다. 이 접수는 자동 시각 판정기가 아니다. 외부 서비스 연결·자동 배정·상시 감시는 없다.

## 실행 Todo와 진행 전달
현재 요청 유형에 맞는 실행 절차를 선택해 전체 주요 단계를 `Tasks.register_execution_plan` 또는 `harness.execution_plan` 명령으로 시작 전에 등록한다. 작업·필수 criteria·명시적 대상 범위를 연결하며 플랫폼을 추측하지 않는다. 현재 런타임에는 별도 Todo 도구가 없으므로 native Tasks가 Todo 원본이다. 승인된 범위에서만 대상을 생성한다. 과거 작업을 연결하면 사후 등록으로 표시한다.
CMD는 `harness.human_progress`로 현재 실행의 체크리스트와 프로젝트 > 단계 > 현재 작업 위치를 읽는다. 대시보드는 동일 상태를 프로젝트 전체의 에이전트 흐름으로 보여준다. 두 화면의 표시 범위/형식은 다르다. [x]는 필수 근거 확인 완료만, [ ]는 나머지이며 실제 관측 중인 항목만 굵게 진행 중으로 표시한다. 주요 전환 때 같은 순서의 전체 목록을 갱신하고 명령마다 반복하지 않는다. 보완/재시도는 기존 항목 아래에 둔다. 검사가 확인하는 목적과 실제 결과를 평문으로 설명하고 명령/원본 로그는 상세에 둔다.
계획 변경·제외는 이유와 근거를 native 이력에 보존한다. 적용 제외를 완료 체크하지 않는다. 호출 요청·실제 프로세스·메인 세션 작업·미검증을 구분하며 이벤트가 오래되면 생존/성공을 추정하지 않는다. 제품 결함/하네스 결함/환경 문제는 근거로 분류하고 미확인은 UNKNOWN. 사용자 판단이 필요한 질문만 명시한다. 현재 작업 완료·제한 시험 PASS를 프로젝트/제품 전체 완료로 확대하지 않는다. 상세는 [공통 진행 규칙](../human-progress.md), [흐름도 기준](../agent-flow.md).
