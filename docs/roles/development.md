# 개발 역할과 담당 범위

[순차 개발 근거 수집](../sequential-evidence.md)을 따른다. 의존 이유·공유 모듈/자원을 선언하고 설정된 명령을 정확한 실행/시도 ID로 래핑한다. 대기는 checkpoint 유형/대상으로, 실제 통합·충돌·재작업은 기존 작업·CR·증거로 기록한다. 인계 시 collection-report의 누락·UNKNOWN을 전달하며 파일 관측을 수정 주체나 병렬화 가능성으로 단정하지 않는다.

문서 상태: **DRAFT**. 공통 책임·인계 계약은 아래 기준을 사용하며, 제품별 빌드 명령·플랫폼별 상세 지침·환경·API 계약은 **UNKNOWN**이다. 제품 선정 후 필요한 범위에서 구체화하며 이 초안을 실제 제품 개발 검증 완료로 취급하지 않는다.

## 책임
확정된 진행 범위의 명세·계약과 제품별 기술 지침에 따라 구현하고 자체 검증 후 검증 역할에 인계한다.
Domain 순수성·DI·모듈 의존성 등은 제품 아키텍처·기술별 지침을 따른다. [Ktor/KMP 참조](../product-architecture.md)는 해당 스택 채택 시에만 적용한다.

## 공통 개발 역할 아래 담당
| 담당 | 책임·인계 |
| --- | --- |
| 백엔드 | API·저장·서버 동작, 요청/응답/오류 계약과 서버 검증 결과 |
| Android | Android UI·플랫폼 연동과 Android 검증 |
| iOS | iOS UI·플랫폼 연동과 iOS 검증 |
| 웹 | 웹 UI·브라우저 연동·키보드/포커스/탐색과 선택 브라우저 검증 |

일반 역할 지침의 담당 구분이다. 명시적으로 구성한 개발 위임 계약은 아래 실제 실행 경로를 사용한다. 제품이 선택한 플랫폼에만 작업을 배정하며 네 담당을 모두 필수로 요구하지 않는다. 대상이 아닌 플랫폼은 N/A와 이유를 남긴다.
공유 코드 담당과 플랫폼별 담당의 소유 모듈·변경 파일을 구분한다. KMP 로직·UI 공유 범위와 웹 기술은 제품별 개발 준비에서 결정하며 웹에 KMP·Compose 또는 별도 프레임워크를 자동 적용하지 않는다. 공유 코드 변경 시 영향받는 선택 플랫폼·담당·작업/PR·재검증 범위를 확인한다.

## 입력·작업 배정
실제 개발 작업에 [프로젝트 결정·단계 계약](../project-settings.md)을 지정한다. UI·클라이언트 연동·신규 서버 구현·통합 검증의 필수 입력을 분리하고 영향받는 작업만 차단한다. API 미정의 임시 계약·목 결과를 실제 연동 완료로 취급하지 않는다. 원본 결정·API·정책·실행 안내는 설정에서 참조하고 중복 작성하지 않는다.
각 작업에 담당 플랫폼·모듈·변경 범위·선행 작업·관련 PR·API 계약 버전·플랫폼별 지침을 지정한다. 기록 양식은 [작업·PR 계약](../task-management.md#work-contract)을 따른다.
요구사항·디자인 명세·시안·시각 검토와 불일치 해결 근거, 제품 기준 커밋·수용 기준, 개발·검증 환경을 받는다.
정책 누락·모순은 기획으로, 디자인 규격 누락·불일치는 디자인으로 반환한다.

## 계약·진행 가능한 범위
백엔드와 관련 클라이언트 담당은 API 요청·응답·오류 계약에 합의하고 인계 기준 버전을 고정한다. 변경 시 영향 작업·담당·PR과 재검증 범위를 식별한다.
계약 준비 후 Mock UI·백엔드의 병렬 구현과 실제 연동 검증 시점은 [작업 관리](../task-management.md#pr-contract)의 의존성 기준을 따른다.
시안이 없거나 미검토라면 진행 가능한 Mock UI·비시각 작업과 가정·차단 범위를 명시한다. 시안이 필요한 UI 최종 검증·완료는 차단한다. 제품 UI 최종 인계 규격은 [디자인 역할](design.md)을 따른다.
병렬 수행·파일 충돌·선행 PR 처리·재개 시 중복 방지는 작업 관리 문서를 따른다.

HTML/CSS 디자인 시안은 샘플 데이터 기반 검토 산출물이며 실제 웹 제품 코드·API 연동·브라우저 검증을 대체하지 않는다.

## 출력
수용 기준별 구현 연결, 변경 이유·산출물·제품 커밋·관련 PR, 자체 검증 PASS / FAIL / NOT_RUN과 근거·환경·제한, 계약/다른 담당/공유 코드에 미치는 영향을 전달한다.

## 완료 조건
담당 범위의 구현과 필요한 자체 검증을 확인하고 같은 명세 버전·제품 커밋·수용 기준으로 검증 역할에 인계한다.
자체 검증 통과만으로 전체 작업을 DONE으로 선언하지 않는다. 선택된 백엔드·Android·iOS·웹의 담당별 검증과 기능 전체 연동 검증을 구분한다.
PR 생성·검증·병합·작업 완료는 [별도 상태](../task-management.md#pr-contract)이며 상호 대체하지 않는다.

## 공통 하네스 결함 수정

[개선 PR 정책](../harness-defect-pr.md)에 따라 제품 정보가 없는 최소 재현을 만들고 kmp_agent 원본의 별도 브랜치·체크아웃/worktree에서 재현 테스트·수정·자체 검증을 수행한다. 설치 사본 직접 수정·현재 사용자 변경 덮어쓰기를 정식 해결로 취급하지 않는다.

정책상 Draft PR까지 자동 준비·제출할 수 있다. 실제 원격 권한이 없으면 가능한 로컬 수정·검증과 PR 제목/본문·제출 diff 목록을 준비하고 미생성 사유를 보고한다. 문제·영향·재현·수정·검증 결과를 포함하며 원본 로그 전체·제품 산출물을 게시하지 않는다. 머지·정식 배포는 사용자 승인 후에만 수행한다. 수정 코드·PR과 배포 후 프로젝트 재검증 완료를 구분한다. 이번 정책 문서 작업에서는 이 절의 실제 개발·PR 작업을 실행하지 않는다.

## 구현 상태
담당 범위·배정·PR 계약은 설계 확정이다. [독립 실행 계약](../role-execution.md)의 development 진입점은 input_interpretation_only 모드로 지정 P/D·전체 자원/AC/검토/기술 지침을 읽고 [입력 해석·계획](../templates/development-plan.md)만 생성한다. READY, 실제 실행, 원문 확인, 의미 검토 완료를 구분한다. 앱·웹 디자인 대상만으로 실제 KMP 구현 타깃을 채택하지 않는다. 제품 구현·빌드·플랫폼 검증·구조화된 PR 자동 실행은 미구현/NOT_RUN이며 입력 해석 완료와 구분한다.

코드 구현 작업은 [개발 추적](../development-tracking.md)의 공통 게이트에서 기존 frozen 입력·대상 Git을 자동 연결하거나 누락 항목을 안내해 차단한다. 문서 작업은 execution_scope=documentation, 현재 역할 실행기의 입력 해석은 input_interpretation_only로 구분한다. 설정이 없는 실행의 제출·검증·인계를 허용하지 않는다.


## 구성된 개발 위임 실행 (2026-10-27 로컬 개발 소스)

기존 input_interpretation_only 경로는 호환을 위해 유지한다. 명시적으로 `configure_delegation`한 코드 작업은 [개발 위임](../development-delegation.md)의 실제 독립 프로세스 경로를 사용한다. 개발 담당은 계약·소유권·의존성을 정하고 필요한 KMP 공통/Web/Server/Android/iOS 작업만 생성한다. 공유 UI는 실제 소스셋과 승인된 공유 범위에 따라 배정하며 플랫폼을 추측하지 않는다.

영역별 실제 변경·명령 결과를 확인하고 별도 통합 명령까지 통과해야 검증 인계가 가능하다. 이 상태는 제품 전체 완료가 아니다. QA 반환은 담당 작업으로 전달하고 [독립 QA](../qa.md)로 다시 검토한다. 자동 실행은 등록된 범위·횟수·프로세스 예산 안에서만 수행하며 새로운 정책 승인을 대신하지 않는다. 설치된 v0.2.0에는 아직 적용하지 않았다.


## 원본·파생 명세 사전 검토
[공통 요구사항 출처·일치 계약](../requirement-lineage.md)을 따른다. 에이전트 파생 문서를 원문/승인 기준으로 승격하지 않는다. 개발 전에 기존 verification 역할의 requirements QA로 전체 원본 목록·항목별 연결·누락·값/동작 변경·제외·승인 의미를 독립 검토한다. 미승인은 기획 보완/필요한 사용자 결정으로 반환한다. 제한 시험은 목적·범위를 명시하고 제품 PASS로 승계하지 않는다. 실행 경로 검증과 제품 요구 충족은 최종 보고에서 분리한다.


## 실행 Todo와 진행 전달
현재 요청 유형에 맞는 실행 절차를 선택해 전체 주요 단계를 `Tasks.register_execution_plan` 또는 `harness.execution_plan` 명령으로 시작 전에 등록한다. 작업·필수 criteria·명시적 대상 범위를 연결하며 플랫폼을 추측하지 않는다. 현재 런타임에는 별도 Todo 도구가 없으므로 native Tasks가 Todo 원본이다. 승인된 범위에서만 대상을 생성한다. 과거 작업을 연결하면 사후 등록으로 표시한다.
CMD는 `harness.human_progress`로 현재 실행의 체크리스트와 프로젝트 > 단계 > 현재 작업 위치를 읽는다. 대시보드는 동일 상태를 프로젝트 전체의 에이전트 흐름으로 보여준다. 두 화면의 표시 범위/형식은 다르다. [x]는 필수 근거 확인 완료만, [ ]는 나머지이며 실제 관측 중인 항목만 굵게 진행 중으로 표시한다. 주요 전환 때 같은 순서의 전체 목록을 갱신하고 명령마다 반복하지 않는다. 보완/재시도는 기존 항목 아래에 둔다. 검사가 확인하는 목적과 실제 결과를 평문으로 설명하고 명령/원본 로그는 상세에 둔다.
계획 변경·제외는 이유와 근거를 native 이력에 보존한다. 적용 제외를 완료 체크하지 않는다. 호출 요청·실제 프로세스·메인 세션 작업·미검증을 구분하며 이벤트가 오래되면 생존/성공을 추정하지 않는다. 제품 결함/하네스 결함/환경 문제는 근거로 분류하고 미확인은 UNKNOWN. 사용자 판단이 필요한 질문만 명시한다. 현재 작업 완료·제한 시험 PASS를 프로젝트/제품 전체 완료로 확대하지 않는다. 상세는 [공통 진행 규칙](../human-progress.md), [흐름도 기준](../agent-flow.md).
