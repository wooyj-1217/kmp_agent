# 개발 역할과 담당 범위

문서 상태: **DRAFT**. 공통 책임·인계 계약은 아래 기준을 사용하며, 제품별 빌드 명령·플랫폼별 상세 지침·환경·API 계약은 **UNKNOWN**이다. 제품 선정 후 필요한 범위에서 구체화하며 이 초안을 실제 제품 개발 검증 완료로 취급하지 않는다.

## 책임
확정된 진행 범위의 명세·계약과 제품별 기술 지침에 따라 구현하고 자체 검증 후 검증 역할에 인계한다.
Domain 순수성·DI·모듈 의존성 등은 제품 아키텍처·기술별 지침을 따른다. [Ktor/KMP 참조](../product-architecture.md)는 해당 스택 채택 시에만 적용한다.

## 공통 개발 역할 아래 담당
| 담당 | 책임·인계 |
| --- | --- |
| 백엔드 | API·저장·서버 동작, 요청/응답/오류 계약과 서버 검증 결과 |
| Android | Android UI·플랫폼 연동과 Android 검증 |
| iOS | iOS UI·플랫폼 연동과 iOS 검증 |

이 구분은 배정할 담당 범위이며 독립 에이전트 자동 호출 구현이 아니다. 대상이 아닌 플랫폼은 N/A와 이유를 남긴다.
KMP를 선택하면 공유 코드의 담당·소유 모듈·변경 파일을 지정하고 Android/iOS 담당의 중복 수정을 방지한다.

## 입력·작업 배정
각 작업에 담당 플랫폼·모듈·변경 범위·선행 작업·관련 PR·API 계약 버전·플랫폼별 지침을 지정한다. 기록 양식은 [작업·PR 계약](../task-management.md#work-contract)을 따른다.
요구사항·디자인 명세·시안·시각 검토와 불일치 해결 근거, 제품 기준 커밋·수용 기준, 개발·검증 환경을 받는다.
정책 누락·모순은 기획으로, 디자인 규격 누락·불일치는 디자인으로 반환한다.

## 계약·진행 가능한 범위
백엔드와 관련 클라이언트 담당은 API 요청·응답·오류 계약에 합의하고 인계 기준 버전을 고정한다. 변경 시 영향 작업·담당·PR과 재검증 범위를 식별한다.
계약 준비 후 Mock UI·백엔드의 병렬 구현과 실제 연동 검증 시점은 [작업 관리](../task-management.md#pr-contract)의 의존성 기준을 따른다.
시안이 없거나 미검토라면 진행 가능한 Mock UI·비시각 작업과 가정·차단 범위를 명시한다. 시안이 필요한 UI 최종 검증·완료는 차단한다. 제품 UI 최종 인계 규격은 [디자인 역할](design.md)을 따른다.
병렬 수행·파일 충돌·선행 PR 처리·재개 시 중복 방지는 작업 관리 문서를 따른다.

## 출력
수용 기준별 구현 연결, 변경 이유·산출물·제품 커밋·관련 PR, 자체 검증 PASS / FAIL / NOT_RUN과 근거·환경·제한, 계약/다른 담당/공유 코드에 미치는 영향을 전달한다.

## 완료 조건
담당 범위의 구현과 필요한 자체 검증을 확인하고 같은 명세 버전·제품 커밋·수용 기준으로 검증 역할에 인계한다.
자체 검증 통과만으로 전체 작업을 DONE으로 선언하지 않는다. 백엔드·Android·iOS 검증과 기능 전체 연동 검증을 구분한다.
PR 생성·검증·병합·작업 완료는 [별도 상태](../task-management.md#pr-contract)이며 상호 대체하지 않는다.

## 구현 상태
담당 범위·배정·PR 계약은 설계 확정, 구조화된 플랫폼/PR 관리·독립 호출은 PLANNED다. 현재 작업 관리의 범위·입력·출력과 문서 참조로만 기록 가능하다. 이번 작업에서는 코드·브랜치·PR을 만들지 않는다.
