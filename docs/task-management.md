# 최소 작업 관리 — 구현 범위

[tasks.py](../harness/tasks.py)는 상태·의존성·문서 산출물·검토·인계·응답 사용량 연결을 관리한다. 전체 자동 에이전트 오케스트레이터나 제품 실행기는 아니다.

<a id="work-contract"></a>

## 프로젝트·기능·실행 작업·PR 계약 — 설계 확정

프로젝트에는 제품 목표·사용자·MVP·정책·채택 스택·아키텍처·디자인 규칙을 연결하고, 그 아래 기능 FEAT와 실행 작업 TASK를 둔다. 첫 제품·스택은 UNKNOWN이며 기존 예제를 자동 채택하지 않는다.
기획은 기능 범위·수용 기준을 구체화하고, 오케스트레이터는 디자인·개발·검증의 판단을 바탕으로 작업·담당·의존성을 구성한다.

| 기록 대상 | 필수 정보 |
| --- | --- |
| 프로젝트·기능 | 프로젝트/제품 참조, 기능 ID·범위·수용 기준, 관련 저장소·제품별 지침 |
| 실행 작업 | 고유 ID·수행 역할·담당 플랫폼/모듈/소유 파일·변경 범위, 입력·산출물·완료 기준, 선행 작업·관련 PR |
| 개발 작업 추가 정보 | 선택 플랫폼(백엔드·Android·iOS·웹 중 해당 범위)·API 계약 버전·관련 담당·플랫폼별 지침·검증 환경·공유 코드와 플랫폼별 코드 소유 범위 |

제품이 선택한 플랫폼에만 배정한다. 공유 코드 변경 시 영향받는 플랫폼·담당·작업·PR·선행 계약과 재검증 범위를 연결하며 웹 담당도 같은 의존성·PR·검증 규칙을 따른다. KMP 로직/UI 공유 범위와 웹 기술은 제품별 개발 준비의 결정으로 남긴다.
작업과 PR은 다른 단위다. 독립적으로 검토·병합 가능한 변경을 PR 하나로 묶고 포함된 작업 ID를 연결한다. 한 작업이 여러 저장소를 바꾸면 저장소별 PR과 기능 전체의 의존성을 기록한다.
새 프로젝트 계층·플랫폼/PR 구조화 필드는 **PLANNED**다. 현재 코드가 지원하는 역할·scope·dependencies·criteria·입출력에는 해당 문서 참조를 연결할 수 있으나 필드 검증·배정 자동화까지 구현된 것은 아니다. 이번에는 YAML 스키마나 실행기를 바꾸지 않는다.

<a id="pr-contract"></a>

## PR 단위·상태·병렬 실행

PR 단위에는 저장소, 브랜치, 기준 브랜치, 관련 작업·담당·API 계약 버전, 검증 근거·제품/명세 버전, 미검증 항목을 연결한다. PR 번호/URL이 없으면 미생성과 이유를 기록한다.
생성 상태(미생성/생성), 검증 결과(PASS/FAIL/NOT_RUN), 병합 상태(미병합/병합), TASK 상태는 별개다. PR 생성·검증 PASS·병합이 작업 또는 기능 전체 완료를 자동으로 뜻하지 않는다.
선행 PR 미병합 시 대기 또는 의존 브랜치 사용을 명시한다. 의존 브랜치를 쓰면 선행 PR·기준 브랜치 관계와 병합 후 갱신·재검증 계획을 남긴다.
병렬 수행은 의존성과 파일 충돌·공유 코드 소유 범위를 확인한 작업에만 허용한다. API 계약이 고정되면 Mock UI와 백엔드는 병렬 구현할 수 있고, 실제 연동 검증은 필요한 구현이 준비된 뒤 수행한다.
재개 전 기존 작업·실행·브랜치·PR과 완료 근거를 확인해 중복 생성·재실행하지 않는다. 확인 불가 상태를 없다고 간주해 새 PR을 만들지 않는다.
PR 자동 생성/조회/병합·병렬 실행기는 **PLANNED**다. 위 내용은 앞으로 배정·검토할 문서 계약이며 이번 작업에서 브랜치·PR을 만들거나 병합하지 않는다.

## 원본과 식별자 — 현재 구현

<a id="demo-feedback"></a>

### 데모 저장소 연결·피드백 환류

일반 제품은 [특정 버전 설치](installation.md)로 선택한 도구를 사용한다. 기존 데모는 개발용 원본 직접 참조를 유지하며 이번에 마이그레이션하지 않는다. 이 개발 모드의 형제 배치에서는 하네스 루트 기준 ../kmp_agent_demo_app/AGENTS.md를 진입점으로 사용한다. 다른 배치의 실제 경로는 [로컬 설정 안내](harness-logging.md#local-setup)에 따라 기록한다. 역할별로 선택한 도구 버전의 roles/README.md에서 해당 역할 문서만 읽는다. 제품 문서는 해당 제품 저장소에서 관리한다.
데모에서 발견한 문제는 데모의 기존 피드백 위치에 먼저 기록한다. 최초 확인 시 빈 저장소라 기존 위치가 없었으므로 단일 docs/feedback.md를 초기 기록 위치로 사용한다. 별도 피드백 서비스·실행기·상태 체계는 추가하지 않는다.

각 기록에 원본 저장소·작업 ID·실행 ID, 기대/실제 결과, 재현 조건·증거, 영향 단계, 사용한 하네스 버전·제품 기준 버전을 남긴다. 분류는 제품 전용 / 공통 결함 / 미분류와 근거를 기록하며, 원인 미확인을 공통 결함으로 확정하지 않는다.
제품 정책·디자인·구현 문제는 데모에서 수정한다. 공통 역할·인계·완료 판정·실행 규칙의 결함이 확인되면 하네스의 기존 작업 관리에 HARNESS_IMPROVEMENT 작업을 등록하고 원본 피드백·데모 작업·증거를 입력 참조로 연결한다.
현재 artifact는 실행 루트 밖 파일을 입력으로 받지 않는다. 타 저장소 원본은 피드백 경로·작업 ID·버전을 상세 작업 문서에서 참조하고, 등록 입력에는 하네스 루트 안의 해당 상세 작업 문서를 사용한다. 하네스 전체를 복사하거나 경로 제한을 우회하지 않는다.

| 과정 | 기존 작업 체계에서 기록할 내용 |
| --- | --- |
| 발견·분류 | 데모 피드백 ID·원본 작업, 분류·근거·담당·차단 단계; 미분류는 결정 전 유지 |
| 개선 | 하네스 개선 TASK와 해당 TODO/READY/IN_PROGRESS 등 기존 상태·원본 참조 |
| 재검증 | 수정 하네스 버전·관련 개선 작업/PR, 영향받는 데모 단계와 PASS/FAIL/NOT_RUN·증거 |
| 해결 | 관련 작업 완료 근거와 데모 재검증 PASS를 연결; 코드/문서 수정만으로 해결 선언 금지 |

발견→분류→개선→재검증→해결은 피드백 처리 과정이며 새로운 TASK 상태 enum이 아니다. 실행 상태는 기존 YAML을 원본으로 유지한다. 무관한 완료 단계는 반복하지 않는다.
제품 변경과 하네스 변경은 저장소별 커밋·PR로 분리한다. PR이 없으면 저장소 경로와 작업 ID를 상호 참조하며 URL·커밋을 만들어 채우지 않는다. 수정 뒤 데모 피드백에 개선 TASK/PR·수정 버전·재검증 결과를 역으로 연결한다.

실행 전 두 저장소의 HEAD, dirty 여부, 사용 문서/구현 경로·SHA-256, 변경 파일 목록과 diff 또는 스냅샷 근거를 고정한다. HEAD가 없으면 UNKNOWN이다. 커밋이 있어도 미커밋 변경 사용을 명시하며 dirty HEAD만으로 재현 가능한 버전이라고 주장하지 않는다. 기존 마스킹·Git 제외 규칙을 유지한다.
공통/제품 지침 충돌은 파일·규칙·영향 단계를 기록하고 적용 중인 상위 지침과 명시적 사용자 지시를 따른다. 두 저장소 규칙 사이에 적용 가능한 우선순위 근거가 없으면 UNKNOWN으로 남기고 관련 결정만 질문한다. 제품 목표·핵심 정책·범위 변경은 사용자 결정이며 가역적 역할 재량은 근거와 함께 처리한다.

### 시행착오 요약·종료·인계

시행착오는 **기대와 실제가 달라 수정·재시도·불필요한 사용자 개입·진행 차질이 발생한 사건**이다.

기록 대상은 도구·실행 오류와 재시도, 요구사항·디자인·계약의 누락 또는 모순에 따른 재작업, 검증 실패·근거 없는 완료 보고·인계 정보 불일치, 모델·환경 문제에 따른 중단·재개, 지침 누락·오해로 발생한 추가 사용자 개입이다.
위 사건의 상세는 기존 로그에 남기며, 회고에는 새로운 원인·반복되는 문제·작업이나 검증에 의미 있는 영향·운영 규칙 변경 중 하나 이상이 있는 사건만 요약한다. 한 번 실패한 뒤 바로 수정됐고 추가 영향이나 배운 점이 없는 명령·패치 오류는 로그에만 남긴다.
정상적인 최초 정책 질문, 계획된 검토, 새 기능 요청, 단순 취향 변경은 원칙적으로 작업 결정·피드백에만 기록한다. 다만 기존 지침 위반이나 정보 누락으로 재작업이 발생했다면 회고 대상이다.

수행 Codex가 종료·인계 시 위 기준으로 새 사건을 확인해 해당 저장소의 docs/retrospective.md를 갱신한다. 해당 사건이 없으면 항목을 만들지 않는다. 기록을 놓쳤다면 재개 시 확인 가능한 근거로 보완한다. README에는 상대 링크와 짧은 설명만 두며 기존 요약을 옮길 때 다른 내용·사용자 메모를 보존한다.

- 하네스 구축·운영은 하네스 회고에, 제품 기획·디자인·개발·검증은 데모 회고에 둔다. 제품에서 발견한 공통 결함은 데모에 발견·영향, 하네스에 공통 원인·개선을 요약하고 상호 참조한다. 상세 내용을 복제하지 않는다. 개선 TASK 연결은 위 저장소 간 환류 기준을 따른다.
- 안정적인 회고 ID와 관련 작업·실행을 연결하고 문제(기대/실제)·영향·근거 링크·대응·재검증 결과만 간결하게 남긴다. 원인·개선 효과 등 미확인은 UNKNOWN, 제안은 미구현으로 표시한다. 교훈이나 긴 도구 출력·상세 경과를 억지로 추가하지 않는다.
- 반복 여부는 동일하거나 근거로 연결되는 원인으로 판단한다. '도구 실행 실패'라는 넓은 분류만으로 묶지 않으며 환경 권한 제한·명령 구문 오류·패치 원문 불일치를 같은 원인으로 간주하지 않는다. 원인이 미확인이면 UNKNOWN을 유지한다.
- 누적 발생은 기존 항목의 발생 횟수·관련 실행 ID·근거와 달라진 영향만 갱신하며 매번 장문을 덧붙이지 않는다. 상세 로그·피드백은 원본을 유지한다. 시간·토큰·이벤트는 기존 로거의 출처·집계 범위를 사용하며 추정·별도 수집하지 않는다. 마스킹·Git 제외 규칙도 유지한다.
- Codex 관리 요약 영역과 수동 메모 영역을 구분한다. 관리 영역만 필요한 부분을 갱신하고 수동 메모 및 영역 밖 사용자 내용은 보존한다. 향후 프로그램 생성 영역이 생기면 별도로 표시하며 수동 영역을 덮어쓰지 않아야 한다.

현재 회고 자동 생성 프로그램은 **미구현(PLANNED)**이며 지침에 따른 Codex 문서 갱신이다. 기존 trial.py report의 JSON·로거 진단 출력은 원본 근거로 유지하며 출력 위치를 변경하지 않는다. 회고 작성·파일 해시 변경은 작업 DONE·재검증 PASS의 근거를 대체하지 않는다.
로컬 회고 파일 갱신과 GitHub 커밋·푸시는 별개다. 이 지침은 커밋·푸시를 승인하지 않으며 이를 근거로 자동 커밋·푸시하지 않는다.

### 최소 상태·기록 구현

- 상태 원본: `.harness/tasks/tasks.yaml`. 외부 의존성 없이 읽는 JSON 문법의 YAML 1.2 부분집합이다. 일반 YAML 문법 전체는 지원하지 않는다.
- Markdown: 상세 명세와 검토 증거. 상태를 별도 원본으로 관리하지 않는다.
- 기능 FEAT-001 아래 TASK-001·TASK-002를 연결하고, 각 역할 수행·검토에 고유 agent_run_id를 발급한다. 상위 run_id는 로거 실행 ID다.
- 상태 변경·등록·역할 시작/종료·검토·인계·사용량 귀속·거부 이벤트에 네 ID를 기록한다. 역할·범위·사용량 귀속 사유는 에이전트 선언이다.
- 입력·출력·증거는 경로·원본 SHA-256·마스킹된 불변 스냅샷 SHA-256·가용 Git 커밋으로 연결한다. 파일 변경 자체는 완료·검증 PASS가 아니다.

상태 저장은 잠금과 원자적 파일 교체를 사용한다. 상태의 outbox를 먼저 저장하고 이벤트를 내보낸다. 로그 기록 후 중단돼도 다음 호출이 같은 이벤트 키로 재전송해 중복을 막는다. 상세 상태·스냅샷·로그는 `.harness/` 아래에 있어 Git에서 제외된다.

| register | 고유 작업·역할·수용 기준·입력 지정 | TODO |
| ready | TODO/BLOCKED, 의존 작업 DONE, 입력 스냅샷 유효, 남은 시도 있음 | READY |
| begin | READY, 지정 역할, 열린 실행 없음, 시도 예산 남음 | IN_PROGRESS·역할 실행 ID 생성 |
| submit | 해당 활성 실행·산출물 있음 | IN_REVIEW·산출물/종료 시각 고정 |
| begin(review=True) | IN_REVIEW, verification/orchestrator, 열린 실행 없음 | 별도 검토 실행 ID 생성 |
| review | 모든 기준 결과·PASS 증거 제출 | 필수 기준 PASS이면 DONE, FAIL/NOT_RUN이면 BLOCKED |
| handoff | 원본 DONE, 대상 TODO, 의존 관계·스냅샷 유효 | 동일 버전 산출물 인계·대상 READY |

재시도에는 새 agent_run_id를 부여하며 기존 기록을 보존한다. 시험 작업의 max_attempts는 1이다. 일반 작업의 시간·토큰·비용 예산, 자동 재시도·중단 역할 복구는 PLANNED다.
증거만 보완하는 [중단·재개 기록](interruption-recovery.md)은 기존 run_id와 완료 단계 ID를 유지한다. 완료 작업은 건너뛰며 현재 작업 상태를 변경하거나 자동 실행하지 않는다.

디자인은 명세 작성·시안 제작·시각 검토 상태를 따로 저장한다. 명세 제출로 시각 검토를 PASS 처리할 수 없다. 필수 시각 검토를 지정한 작업은 NOT_RUN인 동안 DONE을 거부한다. 시각 검토 증거 접수·실행 기능은 PLANNED다.

## 사용자 개입 연결

기존 작업 실행을 task_id·agent_run_id로 지정해 `intervention`을 기록한다. [원문·분류 연결 기준](harness-logging.md#request-classification)의 입력과 절차를 따르며 원문을 수동 수집할 필요는 없다. 아직 수집되지 않은 원문은 pending 선언으로 보존하고 훅 sync 이후 연결한다. 역할·work/review 단계·실행 ID와 작업/디자인 상태는 지정한 실행을 기준으로 기록한다. 이 동작은 원래 작업의 완료 상태·입출력·검토 기록을 변경하지 않는다.

## 사용량

bind_usage는 가져온 원본 `(session_id, response_id)`를 실행 ID에 명시적으로 연결한다. 같은 응답은 여러 실행에 중복 귀속할 수 없고, 같은 귀속 재요청은 무시한다. 원본 사용량·원본 로그는 재작성하지 않는다.
show/report는 귀속한 응답의 실제 증분만 집계한다. 캐시 입력은 입력의 부분집합이며 다시 더하지 않는다. 상충하거나 없는 사용량은 UNKNOWN이다.
역할→작업→기능의 **알려진 소계**를 제공하며 전체 작업·기능 사용량과 비용은 UNKNOWN으로 남긴다. 미귀속 응답을 시간 구간으로 추정해 나눠 배분하지 않는다.

## CLI와 역할 실행 범위

```sh
rtk proxy python3 harness/tasks.py --run-id <run_id> register --data <등록.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> ready --data <작업.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> begin --data <역할실행.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> submit --data <산출물.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> review --data <검토.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> handoff --data <인계.json>
rtk proxy python3 harness/tasks.py --run-id <run_id> bind-usage --data <귀속.json>
rtk proxy python3 harness/tasks.py show
```

JSON에는 해당 메서드의 이름 있는 인자를 넣는다. 예: ready는 `{"task_id":"TASK-001"}`, begin은 `{"task_id":"TASK-001","role":"planning"}`다. 실행 인계 시 입력 버전을 고정한다.

현재 실행 모드는 current_agent(현재 Codex의 역할 수행)와 local_check(로컬 검토 프로그램)다. 독립 모델·하위 에이전트를 생성하지 않는다. 모델 실행 어댑터·역할 자동 호출·원본 응답의 자동 역할 귀속은 PLANNED다.

## 실제 인계 시험

[시험 입력](examples/task-handoff/brief.md) → [기획 산출물](examples/task-handoff/requirements.md) → [기획 검토](examples/task-handoff/planning-review.md) → [디자인 산출물](examples/task-handoff/design.md) → [디자인 검토](examples/task-handoff/design-review.md)를 수행했다.

| 작업 | 결과 | 의미 |
| --- | --- | --- |
| TASK-001 / planning | DONE | 문서 필수 항목·수용 기준·UNKNOWN 연결 검토 통과 |
| TASK-002 / design | DONE | 수용 기준 4개의 화면·상태·행동 연결과 세 상태 분리 검토 통과 |
| 디자인 준비도 | 명세 COMPLETE / 시안 NOT_PRODUCED / 시각 NOT_RUN | 제품 검증·시각 검토 완료와 별개 |

이번 시험만 콘텐츠 스냅샷을 인계 기준으로 사용했다. Git 커밋은 UNKNOWN이며 제품 실행 인계의 Git 버전 고정 요건을 만족했다고 주장하지 않는다.
각 작성 단계의 실제 모델 응답 하나씩을 에이전트가 원본 ID로 귀속했다. 검토는 모델 호출 없는 로컬 구조 검사이며 사용량 미귀속은 UNKNOWN이다. 구조 검사는 제품 정책의 적합성이나 앱 동작을 검증하지 않는다.

시험 결과 조회: `rtk proxy python3 harness/trial.py report --run-id <run_id>`; 보고서는 `.harness/logs/task-trial.json`에 기록한다.
재현 순서는 trial.py의 init → 기획 문서 작성 → submit-planning → review-planning → start-design → 디자인 문서 작성 → submit-design → review-design → report다. 기존 상태를 덮어쓰지 않으므로 새 시험은 새 루트·ID로 수행한다.
