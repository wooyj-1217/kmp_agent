# 운영 설계

아래 기준은 공통 하네스의 설계 계약이다. 제품 목표·기능·원본·인수 조건·테스트 명령과 실험 시나리오·목표치는 적용 프로젝트가 정한다. 제품 기록은 해당 프로젝트에 두고 하네스 원본으로 자동 전송하지 않는다. [최소 로거](harness-logging.md)와 [작업 관리](task-management.md)의 상태·의존성·검토·인계·역할 실행 ID·명시적 사용량 귀속을 구현했다. 기획·디자인의 명시적 독립 순차 실행과 P/D/CR 기준본은 [역할 실행](role-execution.md)에 연결한다. 자동 역할 배정·전체 예산·평가 자동화는 **PLANNED**다.

## 작업 관리

프로젝트→기능→작업의 분해·배정, 담당·의존성·PR과 상태의 기준은 [작업 관리](task-management.md)다. 최소 구현과 설계만 된 필드를 구분하며 문서 계약을 새 런타임 기능으로 표현하지 않는다.

<a id="progress-reporting"></a>

## 진행 보고·조사 위임

이 절은 메인과 역할 에이전트가 공유하는 작업·보고 원칙이다. 지침 전달과 실제 모델의 준수 확인은 구분하며 자동 배정기·보고 생성기·도구 표시 제어를 구현한 것으로 표현하지 않는다.

### 메인의 진행 보고

- 전체 계획·현재 단계·결론·다음 행동 중심으로 보고한다. 작업 시작 시 주요 단계 전체를 체크리스트로 표시하고, 완료한 항목은 체크하며 현재 진행 항목은 강조한다. 간단한 확인은 실제 단계 수에 맞춰 짧게 표시하고 불필요한 단계를 만들지 않는다.
- 주요 단계 전환이나 계획·결과·차단 상황이 바뀔 때 체크리스트를 갱신한다. 도구 호출마다 반복하지 않으며 변화 없는 상태와 “사용자 결정 없음”을 반복 출력하지 않는다. 장시간 진행 중인 작업의 필요한 상태 안내는 생략하지 않는다.
- 조사 결과는 결론과 필요한 근거 위치·미확인 사항으로 요약한다. 파일 내용·검색 결과·원본 명령 출력을 메인 보고에 반복하지 않는다. 재현·승인에 필요한 최소 명령이나 짧은 인용은 목적과 함께 제시할 수 있다.
- 오류·차단은 원인(불명확하면 미확인)·영향·다음 조치를 쉬운 말로 설명한다. 실패나 미실행 검사를 숨기지 않으며 추측을 확인된 원인처럼 쓰지 않는다.
- 세부 로그·원본 근거는 기존 작업·실행·프로젝트 로컬 기록에 보존하고 필요할 때 확인할 수 있는 경로·ID를 연결한다. 요약을 위해 원본을 삭제하거나 마스킹·접근 범위를 약화하지 않는다.

### 조사 위임과 결과 반환

범위가 명확한 다중 파일 조사·비교는 조사 서브에이전트에 위임한다. 간단한 사실·단일 위치 확인은 직접 수행하며 불필요한 위임을 늘리지 않는다. 자동 병렬 스케줄링을 요구하는 규칙은 아니며 기존 의존성·파일 소유 범위와 실행 환경의 권한을 따른다.

위임 입력에는 **전체 목표**, **조사 질문과 위임 범위(대상·제외·읽기/쓰기 권한)**, **기준 버전/기존 변경과 제약**, **결과 반환 형식**을 전달한다. 조사 결과는 다음 세 항목으로 반환한다.

1. 결론: 질문별 답과 근거 수준. 실제 실행·문서상 의도·추정을 구분한다.
2. 근거 위치: 결론을 뒷받침하는 최소 파일 경로·줄 번호, 실행/작업 ID 또는 보고서 위치. 원본 내용·검색/명령 출력 전체를 복제하지 않는다.
3. 미확인 사항: 확인하지 못한 범위·오류·차단과 영향. 필요한 다음 확인을 적는다. 없다면 짧게 표시하고 메인은 변화 없는 부재 보고를 반복하지 않는다.

메인은 반환된 결론을 전체 계획에 연결하고 충돌·부족한 근거를 확인해 다음 행동을 결정한다. 역할의 필수 산출물·검토 근거·기존 JSON 응답 프로토콜은 유지하며 이 요약 형식으로 대체하지 않는다. 명시적인 역할 프로세스에는 전체 목표·범위를 작업의 명시 입력과 scope에 포함하고, 결과 요약은 기존 summary 등에 담는다.

실행 환경이 서브에이전트 호출을 지원하지 않거나 호출이 실패하면 실제 호출·수행이 있었던 것처럼 보고하지 않는다. 그 제약과 영향을 짧게 알리고 가능한 직접 조사로 진행하거나 필요한 확인만 남긴다. 위임 실패도 기존 시도·오류 기록을 보존한다.

### 표시 설정과 적용 경계

이 원칙은 에이전트가 작성하는 진행·최종 보고와 위임 입력/결과를 개선한다. Codex CLI/앱의 “Ran …” 도구 표시를 숨기거나 접는 기능이 아니다. `hide_agent_reasoning`, `model_verbosity`, `tool_output_token_limit`을 도구 카드 숨김 설정처럼 적용하지 않으며 CLI 설치 복구·업데이트는 별도 작업이다.

새 세션은 공통 AGENTS 진입에서 이 절을 읽고, 새 역할 입력은 이 문서가 포함된 동결 definitions를 따른다. 기존 동결 컨텍스트와 설치 릴리스에는 소급 적용하지 않는다. 설치·init·update의 선택 버전 전달 경로는 [설치 안내](installation.md)를 따른다. 지침을 포함한 버전이 배포·선택되기 전에는 새 설치에도 이 변경이 적용됐다고 보고하지 않는다.

<a id="decisions"></a>

## 가정·미결정·사용자 질문

CONFIRMED / INFERRED / UNKNOWN은 요구사항의 근거 수준이다. CONFIRMED는 명시된 결정·확인 가능한 근거, INFERRED는 추론·가설, UNKNOWN은 미확인이다. 조사 사실과 사용자 제품 결정을 구분하며 근거 분류가 진행 허가나 차단 판정 자체는 아니다.
가정마다 **진행 가능 / 확인 전 차단 / UNKNOWN**, 적용 작업·단계, 제안자·근거·영향·재검토 조건을 별도로 기록한다. 진행 판단이 UNKNOWN이면 의존 작업을 임의로 진행시키지 않는다.
역할 재량 안의 가역적인 시각·기술 세부 사항은 직접 제안하고 가정·근거를 남길 수 있다. 사용자 의도·핵심 정책·제품 방향을 그 방식으로 확정하지 않는다.

불명확한 의도·핵심 정책은 기획으로 반환하고 관련 핵심 질문을 묶어서 사용자에게 요청한다. 질문에는 불분명한 점, 필요한 결정, 추천안·대안과 각 선택의 영향을 간결하게 제시한다. 기존 답변·결정 근거를 확인해 이미 답한 내용은 다시 묻지 않는다.
답변 전에는 해당 작업·단계만 차단한다. 응답 부재는 동의가 아니며, 무관한 작업은 계속할 수 있다. 이번처럼 제품을 선정하지 않는 문서 작업에는 미정 제품 정책을 대신 확정하지 않는다.
범위 밖 항목은 제외 근거·후속 작업·담당을 남긴다. 범위 판단이 미정이면 자동 제외하지 않는다. UNKNOWN 수용 기준도 완료 판정에서 일괄 삭제하지 않는다.
요구 변경 시 이유·수용 기준·영향 명세/시안·작업·담당·PR·재검토/재검증을 연결한다.

## 검증과 완료

결과는 `PASS / FAIL / NOT_RUN`이다. 환경 차단으로 미실행한 검증은 NOT_RUN과 사유를 기록한다.
필수 검증이 FAIL 또는 NOT_RUN이면 완료 선언과 DONE 전환을 허용하지 않는다. 거부된 완료 선언도 이벤트에 남긴다.
가정·미결정의 영향과 차단은 위 기준을 적용하고 Mock UI·실제 연동·UI 최종 검증 등을 구분한다.
검증 보고 제출과 제품 작업 통과는 구분한다.

기획의 고유 수용 기준 ID를 사용자 시나리오 → 디자인 명세 → 구현 → 검증 증거에 연결한다.
증거에는 기준 ID, 결과, 재현 절차, 기대·실제값, 검증한 제품 코드 커밋, 요구·디자인 명세 버전, 환경을 기록한다.
미커밋 자체 확인을 최종 제품 커밋의 증거로 대신하지 않는다. 코드·명세 변경 후 영향 범위를 새 버전으로 재검증한다.
요구·정책 문제는 기획, 디자인 문제는 디자인, 구현 오류는 개발로 반환한다.

## JSONL 로그

아래는 전체 실행기의 목표 계약이다. 현재 구현·수동 입력·미지원의 구분은 [최소 로거 상태](harness-logging.md)를 따른다. 작업 종류는 HARNESS_BUILD / HARNESS_IMPROVEMENT / PRODUCT로 구분한다.

실행기가 구조화된 JSONL 이벤트를 자동 기록한다.
`feature_id`, `task_id`, `run_id`, `agent_run_id`로 기능·작업·루프 실행·개별 에이전트 실행을 연결한다.
재시도는 개별 시도로 구분하고 이전 결과를 덮어쓰지 않는다. 모델 호출은 호출 ID로 연결한다.
사건 ID·UTC 시각·실행 내 순번·역할·종류·산출물 및 원인 참조를 기록한다.
실행 시작·종료·오류·중단, 도구 호출, 상태 변경, 인계, 검증, 재작업·재시도, 사람 개입, 완료 선언을 기록한다.
상태 변경에는 전후 상태와 근거, 완료 선언에는 증거와 허용·거부 결과를 남긴다.
사람 개입은 의도된 사용자 결정과 오류·누락 때문에 필요한 개입으로 구분한다.
후속 요청의 분류·환경 복구·UNKNOWN 처리와 기록 절차는 [로깅 기준](harness-logging.md#request-classification)을 따른다. 사용자 원문과 에이전트의 분류 판단을 같은 관측 사실로 취급하지 않는다.
비밀값을 기록하지 않는다. 알려진 패턴의 마스킹·프로젝트 로컬 보관은 구현됐으며, 임의 개인정보의 완전한 탐지와 보존 기간·설정 정책은 미결정이다.

## 하네스 결함 개선 PR 권한

[개선 PR 정책](harness-defect-pr.md)에 따라 적용 프로젝트의 제품/설정 문제·공통 결함·원인 불명을 구분한다. 공통 결함의 최소 재현·원본 격리 수정·검증·Draft PR까지 자동 수행할 수 있으며, 원격 권한이 없으면 로컬 결과·PR 초안과 차단 사유를 보고한다. 제품 원본 로그/산출물 전체를 자동 업로드하지 않는다.

PR 머지·정식 버전 배포는 사용자 승인과 근거를 연결한 뒤 진행한다. Draft PR·머지·배포·프로젝트 재검증/해결은 별도 상태다. 영향 작업만 차단하고 배포 후 프로젝트 업데이트 정책·수정 버전의 검증을 거쳐 재개한다. 이 권한은 운영 정책이며 승인 게이트·자동 실행·상호 참조 집행은 PLANNED다. 실행 범위는 현재 사용자 요청과 [공통 PR 운영 규칙](#pr-submission)을 따른다.

## 버전과 환경

하네스 배포 버전·적용 프로젝트의 피처 버전·제품 릴리스는 별개다. 피처의 기획/디자인/API 기준·CR·Git/SHA·작업/검증 연결은 기존 추적 체계를 사용하며 새 번호 체계를 강제하지 않는다. 하네스 업데이트는 명시적 버전 선택이며 제품 변경 자동 반영 목표와 구분한다.

하네스 버전업 준비는 [지침 정비 절차](releases/README.md#instruction-maintenance)를 거쳐 누적 지침을 정비하고 메인이 검토한 뒤 버전을 확정한다.

배포마다 기존 VERSION·태그/커밋을 기준으로 [지원 현황](releases/README.md)을 릴리스 준비 때 점검·확정한다. 구현 여부와 검증 범위·수동/명령 내부 자동/역할 자동 연쇄를 별도로 기록한다. 미배포 작업본은 HEAD·dirty·미추적 포함 여부·점검 시점을 명시하고 정식 배포에 포함시키지 않는다. 과거 배포 기록은 보존하고 오류 정정은 일자·이유·근거를 남긴다. 개발 작업 진행은 기존 TASK/run 원장으로 관리하며 매 작업 종료마다 지원 표 갱신을 요구하지 않는다. 상세 [릴리스 점검·보존 절차](releases/README.md#릴리스-준비보존정정)를 기존 설치/승인 배포 규칙과 함께 적용한다. 자동 릴리스 집행 기능을 추가한 것은 아니다. GitHub Release 본문은 [공통 작성 지침·템플릿](releases/README.md#github-release-본문)을 사용해 준비 단계에서 초안을 만들고, 최종 배포 커밋·원격 설치 결과 대조 후 확정한다. 이 지침은 자동 생성·게시 기능이나 추가 배포 권한을 뜻하지 않는다.

실행마다 에이전트 정의 해시, 하네스 커밋·버전, 평가 버전, 제품 커밋, 실행 환경을 고정·기록한다.
입력·출력 산출물과 명세 버전을 연결하며 기준 변경은 새 실행으로 구분한다.
초안 작성·검토는 Git 커밋이 없어도 가능하다. 역할 간 실행 인계에서는 문서·API 계약·시안의 경로와 적용할 Git 커밋을 고정하고 해당 제품 커밋·수용 기준 ID를 검증 근거에 연결한다.
기존 하네스 문서 시험은 예외 범위와 원본/불변 스냅샷 해시를 명시해 인계했다. 이는 Git 커밋으로 표현하지 않으며 제품 실행 인계·품질 검증의 버전 요건을 만족했다고 주장하지 않는다. 새 제품 인계에서 버전 정책 예외가 필요하면 사유·범위·승인 근거를 먼저 명시한다.
변경 이력은 Git으로 관리한다. 계약 변경 시 영향 작업·담당·PR과 기준 버전 변경을 기록한다. 해시·버전 변경은 완료·검증 PASS가 아니다.
개발 결과 새 제품 커밋은 초기 입력 커밋과 구분해 기록하고 검증 실행은 실제 검증 대상 커밋을 고정한다.
미커밋 결과를 커밋된 결과로 표현하지 않는다. 기존 Git/SHA·artifact·P/D/CR·개발 코드 상태 추적은 [개발 추적](development-tracking.md)을 따른다. 추가 어댑터·평가 정의의 해시 범위와 환경 고정 세부는 미결정이다.

## 변경 대응 — 목표와 현재 상태

목표는 적용 프로젝트가 정한 감시 대상·변경 확정 조건을 바탕으로 기획·디자인 변경 감지 → 영향 분석 → 관련 구현 수정 → 재검증을 사용자 매번 별도 요청 없이 수행하는 것이다. 원본·이전/새 기준·피처·영향 작업·실행·근거를 연결하고 확정되지 않은 초안을 임의로 반영하지 않는다.
현재는 [개발 추적](development-tracking.md)의 명령·조회 시 해시/유효성 검사와 CR의 선언된 영향·호환성 근거 기록을 지원한다. 감시·변경 확정의 실행 설정, 의미상 영향 분석·자동 수정·전체 재검증은 PLANNED다. RECHECK_REQUIRED 표시는 자동 재검증이 실행됐다는 뜻이 아니다.

## 사용량

모델 호출별 입력·출력 토큰, 제공되는 캐시·추론 세부 항목, 비용·시간을 기록한다.
도구·모델·호출 ID, 원본 필드·단위, 비용 출처 또는 가격표 기준을 보존한다.
세부 토큰이 입력·출력에 포함되면 다시 더하지 않는다. 누적 보고와 최종 보고도 중복 집계하지 않는다.
누락은 `UNKNOWN`이며 0으로 대체하지 않는다. 부분 누락 시 알려진 소계와 누락 범위를 함께 표시한다.
호출 시간과 전체 실행 경과 시간을 구분한다. 추정값은 실제값과 구분하고 방법을 기록한다.
호출 → 에이전트 실행 → 작업 → 기능으로 집계하며 실패·중단·재시도의 토큰·비용도 포함한다.
제공 필드·비용 출처·시간 측정 경계는 실행 어댑터 결정 후 확인한다.

## PR 준비·제출

이 절은 PR을 준비·생성하거나 기존 PR을 보완할 때의 공통 기준이다. 사용자의 원래 요청과 이후 수정 지시, 저장소의 현재 규칙으로 제출 범위와 권한을 확정한다. 특정 브랜치·버전·파일 개수를 기준으로 삼지 않는다.

### 범위 확정과 보존

- “전체 변경”은 마지막 지시·최근 수정 파일만을 뜻하지 않는다. 최초 개발 기준과 현재 커밋·dirty 상태를 고정하고, 기준부터 현재까지 추적·미추적 변경을 조사한다. ignored 파일에도 필요한 구현·자원이 있는지 확인한다.
- 원본·내부 개발본·worktree·설치본의 위치·관계와 각 변경의 출처를 확인한다. 다른 작업자의 무관한 변경은 임의로 포함하지 않는다. 기존 요청·기록·diff로 판단할 수 없는 파일만 사용자에게 질문한다.
- 이관 전에 미커밋·미추적·필수 ignored 자료까지 안전하게 보존하고 복구 가능한 근거를 남긴다. reset·clean·덮어쓰기로 기존 작업을 손상시키지 않는다. 파일 일괄 복사 대신 기준 코드와 diff를 대조한다.
- 구현뿐 아니라 관련 테스트·문서·실행 진입점·필수 정적 자원을 확인한다. 제품 코드·DB·개인정보·원본 대화·대량 실행 로그는 에이전트 제출 자료와 구분한다. 민감 자료를 공개 합성 fixture로 바꾸면 차이와 검증 한계를 기록한다.
- 포함·제외·미해결 파일과 이유, 출처·기준·원본/제출 내용 지문을 범위표로 남긴다. 시험 자료 제외로 필수 검증이 불가능해지지 않는지 확인한다.

### 제출 자료 선별

- PR에는 구축·실행·유지보수·재현 검증에 필요한 구현, 운영 지침, 테스트, 필수 fixture·정적 자원·실행 진입점만 남긴다. 파일의 실제 사용처와 필요성을 확인해 구축 자료와 일회성 검증 기록을 구분한다.
- 특정 작업의 검증 보고서·결과 JSON·캡처·원본 로그·이관 범위표 등 일회성 기록은 PR 제출 대상에서 삭제한다. 이미 PR에 포함했다면 최종 diff에서 제외하고 관련 문서·PR 설명의 링크도 정리한다. 검증 기록이라는 이유만으로 구축 자료에 포함하지 않는다.
- 필요한 증거와 포함·제외 판단은 로컬 또는 승인된 별도 보존 위치에 남긴다. 이 정리는 원본 작업·기존 커밋 이력을 파괴하거나 필수 테스트·fixture를 삭제하는 근거가 아니다. 자료를 제외한 깨끗한 checkout에서도 필요한 검증이 가능한지 확인한 뒤 제출한다.

### 최종 누락 대조

- 원본 개발본의 변경 목록을 제출 직전에 다시 확인하고 PR 최종 diff와 대조한다. 모든 범위 내 변경은 반영되거나 미해결로 드러나야 한다. 파일 개수 일치만으로 내용의 완전성을 판단하지 않는다.
- 제외 이유 기록만으로 기능 누락을 정당화하지 않는다. 요청받은 기능 제외·별도 PR 분리·후속 연기는 사용자 승인 없는 범위 변경이다. 이관할 수 없는 항목은 미해결로 보고하고 전체 반영 완료를 선언하지 않는다.
- 기존 PR 보완 요청이면 같은 PR의 기존 변경을 보존하고 최종 범위에 맞춰 제목·설명을 갱신한다. 독립 검토 가능한 PR 단위를 권장하는 기존 원칙은 임의 분할 권한이 아니다.

### 제출 코드 검증

- 원본 개발본의 PASS로 PR 코드 검증을 대신하지 않는다. 최종 제출 코드를 깨끗한 checkout에서 검사하고 로컬 로그·미추적 파일·개인 절대경로에 의존하지 않는지 확인한다.
- 검증 후 코드가 바뀌면 영향받는 검사를 다시 한다. 동일 코드·입력·환경의 재사용 가능한 검증은 커밋·내용 지문·명령·환경·입력 근거를 남겨 재사용한다. 테스트 삭제·검증 약화로 통과시키지 않는다.
- PR 보고에서는 PASS·FAIL·SKIP·NOT_RUN과 이유를 구분한다. 실제 모델·합성·설치 시험을 별도로 기록한다. 이는 기존 런타임 상태 enum을 확장한다는 뜻이 아니다.
- [범위 검사 도구](pr-scope-check.md)로 누락·미추적 필수 파일·선언한 제외 자료 의존·상대 링크를 확인할 수 있다. 이 도구는 명시적으로 실행하는 목록·해시·존재성 검사이며, 의미상 기능 완전성·숨은 실행 의존·외부 URL 접근성·사용자 승인을 자동 판정하지 않는다. 실제 clean checkout 시험과 사람이 읽는 범위 검토를 대신하지 않는다.

### PR 설명과 실행 권한

- 사용자가 겪는 문제와 변경 후 동작을 먼저 쓴다. 최종 변경·주요 검증·적용 영향·남은 제약을 간결하게 설명하고 상세 범위표·검증 자료는 필요할 때 확인 가능한 별도 보존 위치로 연결한다. 제출 자료는 위 선별 기준을 따르고 일회성 기록은 PR에 포함하지 않는다.
- 대화 경위·잘못된 초기 시도·일시적 도구 오류는 판단에 필요하지 않으면 본문에서 제외한다. 포함 파일과 링크가 PR 브랜치에서 실제 조회되는지 확인한다. 수행하지 않은 검증·자동화 기능을 구현된 것처럼 표현하지 않는다.
- PR 준비·생성과 병합·태그·릴리스·배포·설치본 갱신의 권한을 분리한다. 현재 요청으로 승인된 행동은 불필요하게 재확인하지 않고 수행하되 PR 요청만으로 병합·릴리스까지 진행하지 않는다.
- 공유 브랜치 force-push 등 기존 안전 규칙을 유지한다. Draft 여부는 사용자 요청과 해당 저장소·작업의 규칙을 따른다. 모든 PR을 일률적으로 Draft로 강제하지 않는다. 적용 프로젝트의 공통 결함에는 [개선 PR 정책](harness-defect-pr.md)의 특수 조건이 적용된다.

### 커밋 메시지

- 새 커밋의 제목·본문은 한국어로 작성한다. Conventional Commits를 쓰는 저장소에서는 `feat`·`fix`·`docs` 등의 타입과 scope를 유지하고 설명을 한국어로 쓴다. 코드 식별자·파일명·제품명은 원문을 유지한다.
- 제목은 실제 변경 내용을 구체적이고 간결하게 쓴다. 본문은 필요한 경우 변경 이유·주요 영향·검증을 기록한다. 언어 통일만을 위해 기존 커밋을 재작성하지 않는다.
- 예: `docs(workflow): PR 제출 범위와 검증 규칙 추가`.

### 전달과 보장 범위

공통 진입·오케스트레이터·PR 실행 지침은 이 절을 참조한다. 새 역할 입력에는 운영 지침의 원문·지문이 포함된다. 선택한 코드 버전의 설치·init·update 경로로 지침이 전달되며, 기존 설치본이나 이미 고정된 역할 입력이 자동 갱신되는 것은 아니다. 지침 반영·범위 검사 실행·실제 모델 준수 확인을 구분해 보고한다.
