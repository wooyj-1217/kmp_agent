# 적용 프로젝트에서 발견한 하네스 결함의 개선 PR 정책

## 정책 효력과 이번 변경 범위

이 문서는 운영·권한·인계 정책이다. 정책을 따르는 실행 환경은 아래 범위의 조사·최소 재현·격리된 수정·검증·Draft PR 생성을 매번 별도 요청 없이 수행할 수 있다. PR 머지와 정식 버전 배포는 사용자 승인 후 진행한다. 정책상 허용과 자동 실행 기능의 구현 여부는 별개다.

현재 사용자 요청으로 승인된 조사·수정·커밋·푸시·PR 제출 범위를 따른다. 공통 기준은 [PR 준비·제출](operations.md#pr-submission)이다. 이 문서의 Draft 원칙은 적용 프로젝트에서 발견한 공통 결함 개선에 한정되며 일반 PR 전체에 강제하지 않는다. 설치 사본·제품 코드·다른 작업자의 변경을 임의로 커밋하거나 원본 기본 브랜치에 직접 반영하지 않는다. 병합·릴리스·배포·설치본 갱신 권한은 별도로 확인한다.

## 1. 문제 분류

문제를 발견한 적용 프로젝트의 기존 문제 기록에 기대/실제·근거·분류 판단을 먼저 남긴다. 초기 추정과 조사로 확인한 원인을 구분하고 판단 변경도 이력으로 보존한다.

| 분류 | 판단·처리 |
| --- | --- |
| 제품 요구사항·디자인·구현 문제 | 적용 프로젝트에서 담당 역할로 반환·수정·재검증한다. 제품만의 문제를 하네스 결함으로 승격하지 않는다 |
| 프로젝트 설정 문제 | 설치/연결·단계 입력·명령·경로·권한 등 프로젝트 설정 수정으로 해결 가능한지 우선 확인한다. 정상 설정을 잘못 처리하는 공통 코드라면 근거를 갖춰 재분류한다 |
| 공통 하네스 결함 | 사용하는 하네스 버전의 공통 역할/실행/검증/추적 계약 위반을 최소 재현으로 확인하고 kmp_agent 수정 대상으로 처리한다 |
| 원인 불명 | UNKNOWN과 추가 조사 범위·필요 근거를 기록한다. 재현 실패·권한 부족·로그 부족만으로 하네스 결함을 확정하지 않는다 |

이는 문제의 의미 분류이며 새 TASK 상태나 실행 중 지원되는 issue.kind enum이 아니다. 사용자 개입의 REQUIREMENT_CHANGE/CORRECTION 등 분류와도 별개다. 관련 개입이 있으면 기존 원문/개입 이벤트 ID를 연결한다.

## 2. 조사·최소 재현·격리 수정

1. 적용 프로젝트의 문제 기록에 실제 사용한 하네스 VERSION·커밋 SHA·dirty/mode·설치 출처/선택 ref, 프로젝트와 작업·실행 ID, 기대 동작, 실제 결과, 재현 절차·환경·근거, 영향 작업·검증 항목을 기록한다. 알 수 없는 값은 UNKNOWN과 이유를 남긴다. 설치 정보의 SHA와 실제 실행 코드 버전을 구분한다.
2. 제품 고유 정보·민감 정보를 제외하고 일반화한 최소 재현 사례를 구성한다. 원본 로그·제품 산출물·자격 증명·내부 URL·개인 경로·업무 데이터는 그대로 옮기지 않는다. 합성 데이터·임시 Git 대상과 꼭 필요한 검증 주장만 사용한다. 마스킹 도구만으로 공개 안전성을 보장하지 않는다. 분리할 수 없는 정보는 업로드하지 않고 제외/차단 사유를 기록한다.
3. 사용한 하네스 버전과 수정할 원본 기준을 확인하고, kmp_agent 원본 저장소의 별도 브랜치·체크아웃 또는 worktree에서 재현 테스트와 수정안을 작성한다. 기존 작업·PR이 있으면 이어서 처리하고 중복 생성하지 않는다. 현재 사용자 작업 트리의 변경을 덮어쓰거나 reset하지 않는다. 재현·수정에 필요한 차이만 반영한다.
4. 설치된 `.kmp-agent/releases/...` 사본을 직접 수정해서 정식 해결로 처리하지 않는다. 설치 사본은 원인 조사 입력일 수 있지만 수정·검증·PR은 격리된 원본 작업에서 수행한다. 소스/기준본을 확보할 수 없으면 가능한 로컬 분석·초안을 보존하고 미수행은 NOT_RUN과 차단 사유로 남긴다.
5. 영향 버전에서 실패를 확인하는 재현 테스트, 수정 후 통과, 관련 회귀·영향 검증을 수행한다. 테스트 명령·환경·기준/결과 코드 상태·출력 해시·PASS/FAIL/NOT_RUN을 남긴다. 재현되지 않으면 해결로 단정하지 않으며 검증 불가 범위도 공개 가능한 근거에 명시한다.

## 3. Draft PR과 권한 경계

원격 접근·브랜치 게시·PR 생성 권한이 있으면 관련 검증 후 kmp_agent 원본 저장소를 대상으로 **Draft PR**을 생성한다. 설치 출처와 프로젝트의 저장소 설정으로 대상/기준 브랜치를 확인하며 임의의 원격으로 게시하지 않는다. 정책 범위의 정제된 최소 재현·수정·검증 제출에는 건별 추가 공유 승인을 요구하지 않는다. 제품 로그 전체나 제품 산출물을 자동 업로드하지 않는다.

PR에는 다음을 포함한다.

- 문제와 기대/실제 결과, 공통 결함 판단 근거.
- 영향 하네스 버전·공통 기능·작업/검증 범위와 남은 불확실성.
- 제품 정보가 없는 최소 재현 절차·실행 명령과 재현 테스트.
- 수정 내용·변경 이유와 관련 회귀 검증 결과·미검증 항목.
- 하네스 개선 TASK·검증 근거 참조, 제안 해결 버전/배포 필요성. 미배포 버전을 실제 해결 버전으로 표시하지 않는다.

적용 프로젝트의 문제 기록에 실제 생성된 PR URL과 하네스 개선 작업을 연결한다. 공개하면 안 되는 프로젝트 ID·문제/작업/실행 ID·비공개 경로의 대응표는 프로젝트에 유지하고, 공개 PR에는 정제한 하네스 측 ID·근거만 사용한다. URL이 없으면 만들어 채우지 않는다.

원격 접근·인증·권한·연결 정보가 부족하면 가능한 로컬 재현·수정·검증을 끝내고 PR 제목·본문·제출할 diff/파일 목록까지 준비한다. PR 상태는 미생성으로 남기며 부족한 권한/정보·실패 근거·재시도 조건을 보고한다. 이는 Draft PR 생성 완료가 아니다. 권한을 우회하거나 설정·비밀값을 추측하지 않는다.

Draft PR 생성·검증 PASS·머지·정식 배포·적용 프로젝트 해결은 각각 다르다. **PR 머지와 정식 버전 배포(릴리스 태그·게시 포함)는 사용자 승인 후에만 진행한다.** 승인 근거에는 대상 PR/커밋·배포 버전·허용 작업과 실제 사용자 승인 메시지 참조를 연결한다. 머지 승인을 배포 승인으로 자동 간주하지 않는다.

적용 프로젝트가 명시한 영향 작업만 차단하고 관련 없는 제품 작업은 계속할 수 있다. 원인 불명일 때도 위험을 확인한 범위를 기록하며 프로젝트 전체를 근거 없이 차단하지 않는다.

## 4. 배포 후 업데이트·재검증·재개

수정 버전이 승인 후 배포되면 적용 프로젝트의 업데이트 정책에 따라 실제 ref/SHA를 선택해 반영한다. 정책상 자동 적용이 허용된 환경에서도 선택 버전·적용 근거를 기록하며 원본 최신 HEAD로 조용히 전환하지 않는다. 현재 설치기는 명시적 update만 지원하며 업데이트 정책 자동 실행기는 미구현이다.

적용된 버전·코드/시작 입력·훅 상태를 확인하고, 차단된 작업과 영향받은 검증을 **수정 버전에서 재실행해 통과한 뒤 재개**한다. 연결/수집 검증 PASS만으로 원래 결함의 해결을 선언하지 않는다. 실패하면 이전 실패와 새 결과를 모두 남기고 해당 작업의 차단을 유지한다. 필요한 재개는 기존 checkpoint/resume 또는 새 작업/검증 실행을 사용하며 완료 단계나 과거 근거를 덮어쓰지 않는다. checkpoint는 실행 재개용이며 코드 복원을 보장하지 않는다.

각 실제 실행의 하네스 버전·SHA·dirty/mode를 기록한다. 기존 실패 문제 → 개선 TASK/실행 → 수정 PR → 승인/배포 근거·해결 버전 → 프로젝트의 적용 ref → 재검증 실행·증거 → 재개 실행을 연결한다. 과거 실행을 새 버전으로 재표기하지 않는다. 현재 이벤트의 harness 값은 해당 로거/도구 런타임 관측이며 과거 모델 실행 버전을 추정하는 근거로 사용하지 않는다. 과거 사용 버전이 확인되지 않으면 UNKNOWN과 사유를 보존한다. 하네스 배포 버전과 제품 피처의 P/D/API/CR·Git 기준 및 제품 릴리스는 독립적으로 관리한다.

## 5. 기존 추적 구조 재사용

| 연결 | 기존 체계와 기록 위치 |
| --- | --- |
| 발견·분류 | 적용 프로젝트의 기존 문제/피드백 문서·ID와 관련 TASK. 원문·제품 고유 근거는 프로젝트에 보관 |
| 하네스 개선 | 원본 저장소의 HARNESS_IMPROVEMENT 작업, 기존 feature_id/task_id/run_id/agent_run_id·scope/dependencies/criteria |
| 최소 재현·수정·검증 | 기존 artifact snapshot·Git/코드 상태·기준 입력·검증 결과/유효성. 원본 체크아웃에는 정제된 사례만 보관 |
| 변경 근거 | 필요한 기존 CR·입력 전후 기준·호환성 근거·영향 TASK/검증·관련 개입 이벤트 참조. 별도 버전 번호나 문제 DB를 만들지 않음 |
| PR·승인·배포·재개 | 기존 [작업·PR 계약](task-management.md#pr-contract), [설치/버전 기록](installation.md), 문제·상세 작업 문서의 상호 참조 |

경로/문서 참조는 각 실행 루트의 기존 artifact 입력으로 연결한다. 다른 저장소의 원본을 읽기 위해 경로 제한을 우회하지 않으며, 하네스 작업에는 정제한 로컬 재현·상세 문서만 입력한다. 원본 저장소별 ID가 같아도 동일 작업으로 취급하지 않는다.

현재 `findings.py`의 issue.kind는 design/requirements/policy만 지원한다. 이 정책의 설정/하네스/원인 불명 분류를 지원하는 것처럼 새 kind를 보내지 않는다. 지원되는 반환은 기존 issue를 사용하고, 나머지는 기존 문제 문서·작업 scope/criteria/입력 참조로 기록한다. 구조화된 저장소 간 문제·PR·해결 버전의 자동 검사는 후속 구현이다.

## 6. 역할별 책임

| 역할 | 정책에서의 책임 |
| --- | --- |
| 오케스트레이터 | 분류·원인 불명 조사·설정 확인을 조정하고 영향 작업만 차단. 제품/하네스 작업·PR·버전·업데이트/재개와 승인 대기 연결 |
| 개선 | 공통 결함 판단 근거·정제한 최소 재현·개선 범위·영향과 수정 후 효과를 정리. 제품 문제를 무조건 하네스 결함으로 올리지 않음 |
| 개발 | 별도 원본 작업 공간에서 재현 테스트·수정·자체 검증과 Draft PR 초안/제출을 준비. 설치 사본·무관한 변경을 정식 수정으로 게시하지 않음 |
| 검증 | 실제 사용 버전/코드 상태와 재현·회귀 근거를 확인. 로컬 수정 검증과 배포 후 프로젝트 재검증을 구분하고 PASS/FAIL/NOT_RUN 보존 |

이 역할 분담은 독립 프로세스나 전체 자동 실행기가 구현됐다는 의미가 아니다.

## 7. 현재 지원과 후속 구현 — PLANNED

현재 재사용 가능한 구현은 작업/실행 ID, 상태·의존성·검토·인계, snapshot·CR, 대상 Git 코드 상태/검증 유효성, 이벤트의 런타임 버전, 명시적 설치/update다. 이 정책의 자동 절차·공유 권한 집행·머지/배포 승인 게이트는 문서 계약이며 런타임 보장은 아니다.

후속 구현은 다음과 같다.

- 네 가지 문제 분류·추가 조사·설정 우선 확인과 영향 작업만 차단하는 실행 연결.
- 제품 정보 제외·최소 재현 생성/검토와 격리 브랜치·체크아웃/worktree 수명주기, 기존 작업/PR 재사용.
- 원격 권한 확인·Draft PR 생성·URL 역연결·권한 부족 시 로컬 초안 보존, 머지/정식 배포 승인 집행.
- 기존 문제·작업/실행·CR·PR·배포/해결 버전·프로젝트별 재검증/재개를 자동 연결·검사하는 참조 규격.
- 프로젝트 업데이트 정책 실행, 실제 사용 버전별 재검증·차단 해제·재개와 실패 이력 보존.

프로젝트별 업데이트·게시 대상·권한 설정 인터페이스는 미정이며 현재 스키마에 없는 키나 새 상태를 구현된 것처럼 추가하지 않는다. [미결정 사항](open-decisions.md)과 [설계 구현 상태](../design.md#구현-상태)를 따른다.
